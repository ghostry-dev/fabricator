# TypeBox

Any Schema can be converted to a [TypeBox](https://github.com/sinclairzx81/typebox) schema. Use this to validate fabricated data, or to use one shape for both test data and runtime validation.

```ts
import { toTypeBox } from "@ghostry/fabricator-adapter-typebox-v0";

const TProduct = toTypeBox(ProductSchema);
```

## Adapters are values, not names

An adapter is an ordinary value you import. There is nothing to register, and fabricator itself doesn't know about any schema library. Each adapter carries its own key, and `.adapt()` stores an override under that key. So two adapters never collide, and naming the wrong adapter is an import error instead of an override that is silently ignored.

This also lets adapters for two versions of the same library work side by side: one schema can carry an override for each.

## The default mapping

Each kind maps to one fixed TypeBox counterpart:

| Kind               | TypeBox                                                |
| ------------------ | ------------------------------------------------------ |
| `object`           | `Type.Object({ ...fields })`                           |
| `array`            | `Type.Array(element, { minItems, maxItems })`          |
| `tuple`            | `Type.Tuple([...items])`                               |
| `record`           | `Type.Record(key, value)`                              |
| `object.omittable` | `Type.Optional(inner)`                                 |
| `object.optional`  | `Type.Optional(Type.Union([inner, Type.Undefined()]))` |
| `always`           | a pinned literal (see below)                           |
| `opaque`           | `Type.Unknown()`                                       |
| `bigint`           | `Type.BigInt(bounds)`                                  |
| `boolean`          | `Type.Boolean()`                                       |
| `enum`             | `Type.Union([...pinned literals])`                     |
| `choice`           | `Type.Union([...option schemas])`                      |
| `date`             | `Type.Date(timestamp bounds)`                          |
| `number`           | `Type.Number(hints + bounds)` or `Type.Integer(...)`   |
| `string`           | `Type.String(hints + minLength/maxLength)`             |
| `symbol`           | `Type.Symbol()`                                        |
| `undefined`        | `Type.Undefined()`                                     |
| `undefinable`      | `Type.Union([inner, Type.Undefined()])`                |
| `null`             | `Type.Null()`                                          |
| `nullable`         | `Type.Union([inner, Type.Null()])`                     |
| `nullish`          | `Type.Union([inner, Type.Null(), Type.Undefined()])`   |
| `recursive`        | `Type.Recursive(...)`, `$ref`-based                    |

For `number` and `string`, hints passed as `.as(produce, { format, pattern, multipleOf })` are added as JSON Schema keywords alongside the `whereby` bounds. Inclusive bounds become `minimum`, `minLength`, or `minItems`. An exclusive value bound becomes `exclusiveMinimum` with the value you gave. JSON Schema has no exclusive length keyword, so an exclusive length becomes the nearest inclusive whole number.

## When the default is wrong

```ts
import { typebox } from "@ghostry/fabricator-adapter-typebox-v0";

T.string
  .whereby({ length: { max: 254 } })
  .adapt(typebox, () => Type.String({ format: "email" }));
```

`.adapt(adapter, produce)` overrides the mapping for one schema. The override stays through later calls, so `.whereby()`, `.as()`, or `.extend()` after `.adapt()` keep it. To adapt to several libraries, chain several `.adapt()` calls. Each one only replaces its own adapter's override.

Because you pass the adapter itself, its types are known at the call site. A producer that returns something TypeBox can't produce is a type error right there, not a silent problem at conversion time.

### What the producer is handed

The producer gets one argument, `{ schema, meta }`. Destructure whichever part you need.

`meta` is the schema's own config, so an override can build on what you already told fabricator instead of repeating it:

```ts
T.string
  .whereby({ length: { max: 254 } })
  .adapt(typebox, ({ meta }) =>
    Type.String({ format: "email", maxLength: meta.whereby.length.max.value }),
  );
```

Its shape depends on the kind: `whereby` for a `string`, `definition` for an `object`, and so on. You can read it, but it isn't a stable API. An override that reads `meta` may break when its shape changes between versions.

`schema` is the schema being adapted, with the override it replaced. So `toTypeBox(schema)` inside a producer gives the previous override, or the default mapping if there was none. That is what makes intersecting with it work the way it reads:

```ts
email.adapt(typebox, ({ schema }) =>
  Type.Intersect([toTypeBox(schema), Type.String({ minLength: 3 })]),
);
```

Both are read at conversion time, not when `.adapt()` is called, so the producer sees any builder methods chained after it.

## Kinds that need `.adapt()` more than most

**A `record` keyed by `T.symbol`** throws. TypeBox's `Type.Record` can't represent a symbol key, and returning a schema nothing can pass would be worse than an error. Use `.adapt(typebox, ...)` to supply your own.

**`opaque`** always maps to `Type.Unknown()`, because the adapter can't know what your producer returns. If the static type matters, adapt it.

## Where `Static<ToTypeBox<S>>` and the fabricated value type can legitimately diverge

These cases are all expected, and none is a bug:

1. **An adaptation.** You told TypeBox something fabricator doesn't follow, so keeping the two compatible is up to you.
2. **`always`/`enum` over a value TypeBox can't type exactly.** TypeBox has no literal type for a `bigint`, `Date`, `symbol`, or `Uint8Array`, so the static type is the general one, such as `bigint`. TypeBox still checks a `bigint` or `Date` against the exact value at runtime, but it can't check a `symbol` or a `Uint8Array`'s contents.
3. **A `record` over a fixed set of literal keys.** TypeBox turns this into a `TObject` with every property _required_, while the fabricated type is `Partial`. A record's size is random and duplicate keys collapse, so a schema with two possible keys may produce only one.
4. **`opaque`.** `Static<TUnknown>` is `unknown`, while the fabricated value has the producer's exact return type.

Only the last is purely wider, and always safe. In the others, the two types say genuinely different things about the same field.
