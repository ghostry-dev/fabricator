# fabricator — architecture notes

Context for working on this codebase across sessions. Not user-facing — this is how the machine works and where the traps are.

**While this library is 0.x, do not avoid breaking changes.** Semver-0 is the window for getting the shape right; compatibility with existing call sites is not a reason to keep a worse API, name, or invariant. Prefer correct design over a compatibility shim. Tests still pin behavior — this is not a license to break things accidentally.

## Mental model

Three layers, always in this order:

1. **Registry** (`T`, from `initialize({ types })`) — a namespace of builder functions/objects, one per primitive kind (`T.string`, `T.object`, …). Calling/accessing one produces a **Schema**.
2. **Schema** — inert, serializable data: `{ [Kind]: "...", [Meta]: {...} }` plus kind-specific builder methods (`.whereby()`, `.as()`, `.extend()`, …). Building a Schema never touches randomness. Schemas compose freely (`T.object({...})`, `T.array(T.string)`, `.extend()`, `.refine()`, `.override()`) and can be passed around, stored, and reused.
3. **Fabricator** (`new Fabricator(schema)`, from `initialize()`'s returned `Fabricator` constructor) — a live, built object with `.fabricate()`. Building is where randomness is drawn and attached (see "Randomness"). A Schema is inert; a Fabricator is loaded.

`initialize({ salt, algorithm, types, clock })` mints one isolated instance — its own `RandomSource`, `T`, and `Fabricator` constructor. Nothing is module-level shared state; two `initialize()` calls (e.g. parallel tests) can never perturb each other.

## Package layout

Three packages under `pkg/`:

- **`pkg/fabricator`** — core. This document's `src/`/`test/` mentions are relative to `pkg/fabricator/` unless said otherwise.
- **`pkg/fabricator-adapter-typebox-v0`** — TypeBox adapter, published separately. `-v0` because `@sinclair/typebox` and the unscoped `typebox` package are unrelated; a future `typebox` 1.x adapter is a sibling (`pkg/fabricator-adapter-typebox-v1`) with its own hard peer dependency, not a second concept folded into this one. The adapter is one file, `pkg/fabricator-adapter-typebox-v0/src/index.ts`. This document still calls it "`Adapter/TypeBox`" or "the TypeBox adapter module" — a module name, not a path.
- **`pkg/fabricator-extension-faker-v10`** — the faker extension (see below). `-v10` pins `@faker-js/faker` 10.x; a faker 11 extension is a sibling with its own peer range. **`extension`, not `adapter`:** an _adapter_ converts a Schema outward (`Adapter/Types.ts`'s `{ key, convert }`, `.adapt(...)`); an _extension_ adds builders inward through `registry.extend(...)`. They compose — faker builders convert through the TypeBox adapter like any other schema — but they are unrelated mechanisms, and nothing in `Adapter/` is involved in an extension.

Core has four entry points, one per audience: **`.`** is for using fabricator (`initialize`, `T`, and everything an ordinary call site needs, `Adapting` included — see "Adapting to an external schema library"); **`pkg/fabricator/src/adapting.ts`**, published as `@ghostry/fabricator/adapting`, is the contract an external adapter package implements against (`Adapter`, `Recurse`, `walk`, `Adaptation`, `AdaptationsOf`) — named for the activity rather than the `Adapter` noun, the same pattern `@ghostry/fabricator/harnessing` follows; **`pkg/fabricator/src/harnessing.ts`**, published as `@ghostry/fabricator/harnessing`, is the integration a test-framework wrapper (`@ghostry/harness`) drives, satisfied structurally with no dependency in either direction (see "Harnessing integration"); **`pkg/fabricator/src/internal.ts`**, published as `@ghostry/fabricator/internal`, is the only way an adapter reaches `Kind`/`Meta`/`Buildable`/`isPlainObject`/`Fabrication`/`NaiveFabricator` and each primitive's `.Core` via `Primitive.<kind>` (for "Match `Core`, never `Schema`") without putting those on the end-user `.` export. `internal.ts` is also core's white-box test route into internal modules (`Random`, `Schema/Registry` neighbors, `Enumeration/Plan`, `Primitive/*`). Tests import via package specifiers so `bun test` hits `dist/`, not source (see "Tooling / conventions"). New leaf kinds need an entry in `Primitive/namespace.ts` (re-exported from `internal.ts` as `Primitive`).

Non-core packages resolve `@ghostry/fabricator`/`@ghostry/fabricator/adapting`/`@ghostry/fabricator/internal` as real specifiers: `node_modules` → workspace symlink → core `exports` → `dist/`. No source fallback: core must be built before dependents' `check`/`test` resolve (`bun install` alone is not enough). The faker extension also needs the adapter's `dist/` (devDependency, for its adapter tests). Build order is core → adapter → extension (root `build` enumerates that). Core's own `check`/`test` need core `dist/` the same way. Package `check`/`test` scripts do **not** build; root `check`/`test` run `bun run build` first, then each package in order. Running a package script cold fails with `Cannot find module`.

`docs/` is outside the Bun workspace (own `package.json`/`bun.lock`). Package `jsr.json` `publish.exclude` need not name `docs`/`.github`/`AGENTS.md` — they live outside every `pkg/*`, not as excluded siblings the way they would if `jsr.json` sat at the repo root.

**Root `overrides: { "@ghostry/fabricator": "workspace:*" }` is required for `bun install`, not just a pin.** Dependents declare a real peer range — a lower bound and a `<0.1.0` ceiling (the adapter is at `>=0.0.3 <0.1.0`, the faker extension at `>=0.0.1 <0.1.0`), never `^0.0.1`, since a caret on `0.0.x` pins the patch and `^0.0.1` is only `0.0.1`. Changing that peer-range text at all makes bun drop the lockfile cache and re-resolve; for `peerDependencies` it queries npm rather than the same file's `devDependencies: { "@ghostry/fabricator": "workspace:*" }`. Don't remove it without re-checking `bun install` after any peer-range edit. **That peer range cannot express a symbol moving between core's entry points** — a published adapter version built against an older core still satisfies `>=0.0.1 <0.1.0` after a symbol moves from `.` to `./adapting` (or vice versa), then fails to resolve the moved symbol at runtime. Release core and every dependent that imports the moved symbol in lockstep, and raise the dependent's lower bound to the core version that made the move.

## The symbol-tagged shape

Every Schema and every built Fabricator carries the same well-known symbols (`src/Types.ts`), never string keys, so they can't collide with a user's field named `kind` or `meta`:

- **`Kind`** — a string literal tag (`"string"`, `"object"`, `"object.compute"`, `"object.omittable"`, …). The dispatch key everywhere: `Constructor.ts`'s switch, `violatesKind`, `ToTypeBox`'s mapped-type dispatch, every `isXFabricator`/`isXSchema` type guard.
- **`Meta`** — the kind's own config blob (`{ whereby, produce, ... }`). Opaque outside that kind's files.
- **`Produces`** — a _phantom_ marker (`[Produces]?: $T`), no runtime meaning. Exists so `ValueOf<$Schema>` (`Schema/Types.ts`) can read a Schema's eventual value type _before_ it's built, without importing every kind (which would cycle for `object`/`array`, which can nest anything). **Except**: `boolean`/`date`/`number`/`symbol`'s `Registry.ts` each explicitly set `[Produces]: undefined as unknown as Fabricated` on their bare/default top-level export — see "the declaration-emit trap"; that assignment is load-bearing and must not be removed.
- **`trace`** — a required property on every built Fabricator (`Random/Types.ts`'s `Trace`), not a well-known symbol. Recording is unconditional: a node that never draws (a bare `object`/`tuple`/`always`/`null`/`undefined`/`symbol`, `object.compute`, `recursive.self`, `number.sequence`) still carries one, which is what makes `new Fabricator(schema, node.trace)` able to replay a nested subtree. Minting a stream from it (`toStreamFromTrace(algorithm, trace)`) is still paid only by nodes that draw. Slots, in encode order: `salt` (the _instance_ salt), `clock` (construction "now," epoch ms), `path`, `kind`, `ordinal`. Every slot is part of `encode`, so `toStream(algorithm, encode(trace)).seed === stream.seed` stays exact. `always`/`null`/`undefined` never mint a stream — none has an `.as()` — but they still record. `object.compute` never mints one either (no stream-driven `produce`); `.as(...)` is the opposite, since `produce` is handed a `ProduceContext` that requires a stream.
- **`Fixed`** — baked onto a field's Schema entry by `object.override(...)`; read only by `Constructor.ts`'s `make`, which still dispatches that field before discarding the result in favor of the fixed value — not for stream-parity (structural path keying means skipping a dispatch can't shift any sibling's stream), but to detect via the built Fabricator's `[Kind]` whether the field was originally `object.compute`, so an overridden compute field resolves in phase 1 like any ordinary field. See "Randomness."
- **`Replace`** — a directive consumed by `deepMerge`/`shallowMerge`: the right-hand operand wins wholesale instead of merging into the left.
- **`Adaptation`** — a per-adapter map of external-schema overrides, keyed by each adapter's own `key`, written by every kind's `.adapt(adapter, produce)` and read only by an adapter. Exported from `@ghostry/fabricator/adapting`, not `.` — implementing an adapter's business, not an ordinary caller's (see "Adapting to an external schema library"). Completely inert for fabrication: nothing in `Constructor.ts` or any kind's `Fabricator` looks at its contents. `boolean`/`date`/`number`/`symbol`'s `Registry.ts` must assign it at their top-level spread for the same declaration-emit reason `[Produces]` must.
- **`Omitted`** — used by both `T.omittable` and `T.optional`. Publicly exported. Internally, `object.omittable`'s/`object.optional`'s Fabricators return it when their roll lands on omission (read by `object`'s fabricate loop, which then omits the key entirely — never writes `undefined`); publicly, it's the value you pass to `.override()`/`.fabricate(overrides)` to force an omittable or optional key off. Not named `Omit`, which would collide with TypeScript's built-in `Omit<T, K>` (already used in `object/Schema.ts`, `Utility/DeepMerge.ts`, `Utility/ShallowMerge.ts`).
- **`Children`** — the Fabricators that exist at build time: whatever `Constructor.ts`'s `make` already constructed for this node's nested schemas before handing them to the kind's own `Fabricator()` factory. Carried by every composite kind whose construction receives already-dispatched Fabricators — `object` (its `Fields` map), `tuple` (`elements`, in slot order), `derive` (the dispatched `from` slots, in `[Meta].from` order), `choice` (the dispatched options, in `[Meta].items` order — weights stay in `[Meta]`), `array` (the single shared `element`), `record` (`{ key, value }`), and each of `nullable`/`nullish`/`undefinable`/`object.omittable`/`object.optional` (the single wrapped `source`). The payload shape is kind-private, exactly as `[Meta]` is. `recursive` carries none — its expansions are a function of draws made _during_ `fabricate()`, one throwaway Fabricator per `self` occurrence, so there is no stable child at build time (`body`/`terminal` are already on `[Meta]` as ordinary sub-Schemas).
- **`Layer`** — the one symbol in this list that tags a _config value_ (a `Salt`, via `layer()`, `Utility/Core.ts`) rather than a Schema or Fabricator. Read by `Fabricator/Constructor.ts`'s `resolveScope` for `new Fabricator(schema, { salt: layer(...) })`, which composes `[Layer]`'s wrapped salt onto the instance's own salt (`[...instance.salt, ...salt]`) rather than replacing it. `layer()` is its only producer; a caller never names the symbol directly, the same convention `replace()`/`[Replace]` sets.

## Anatomy of a primitive

Every leaf kind lives in `src/Primitive/<name>/` as five files (compare `always`, `boolean`, `symbol`, `undefined` for the simplest; `number`, `string`, `date` for real config surface), plus `Outcomes.ts` when the kind has a named outcome list:

- **`Types.ts`** — plain type aliases only, no runtime code. `Fabricated` (the value type), `Meta` (config shape), `Core` (the `[Kind]`/`[Meta]`/`[Produces]`/`[Adaptation]` structural shape every Schema/Fabricator of this kind shares). `Core`'s trailing `$Adaptations extends Adaptations = {}` parameter carries an adaptation through the type level; every kind has it, and its default keeps existing `Core<$Meta>` references working. **Every kind has all three, with no exceptions** — see "Match `Core`, never `Schema`." A value export in this file is a module-kind change, not a local addition: `export type Fabricated = boolean` (or `string`) in a value module, under `export * as boolean`/`string` in `Primitive/namespace.ts`, resolves the name to the namespace instead of the TypeScript primitive and drops `[Kind]`/`[Meta]` off `Core`.
- **`Outcomes.ts`** — the runtime tables that must not live in `Types.ts`: `outcomes` for `boolean` and the presence wrappers (`nullable`/`nullish`/`undefinable`/`object.omittable`/`object.optional`). Re-exported from the kind's `index.ts` so `Primitive.boolean.outcomes` still resolves.
- **`Schema.ts`** — the `Schema` type/function, generic over the same trailing `$Adaptations` its `Core` is, threaded through every builder method's return type so chaining doesn't drop an adaptation. Always adds `.adapt(adapter, produce)` (see "Adapting to an external schema library"), and usually adds `.as(produce)` to layer an opaque custom producer on top of whatever config already exists (carrying it forward, not discarding it, so it survives for future validation). `always` is the one kind with no `.as()` at all — a fixed value has nothing meaningful left to override. `object.compute` and `T.derive` finish with a required `.as(resolve)` on the factory instead of a re-`.as()` on the Schema. `object.omittable`'s `.as(produce)` is the usual idiom but `produce` may itself return `Omitted`, replacing the presence roll _and_ the value draw with one opaque function.
- **`Fabricator.ts`** — the `Fabricator` type/function: turns a built Schema into something with `.fabricate()`. This is where `Kind`-specific randomness is drawn. Every kind's `Fabricator(...)` takes a single `FabricatorContext<$Schema>` (`Fabricator/Types.ts` — `{ schema, algorithm, trace }`); a kind-specific extra (an array's `element`, an object's `fields`) still follows as its own trailing parameter. `always`, `null`, `undefined`, `object.compute`, and `recursive.self` never call `toStreamFromTrace` — none of them draws randomness of its own — but they still receive the context, for `trace`.
- **`Registry.ts`** — what becomes `T.<name>`. Either a bare `Schema({...})` object with extra builder methods spread on (`boolean`/`symbol`/`number`/`date`/`undefined` — usable with no call at all, e.g. `T.boolean`), or a factory function (`always`/`array`/`object`/`omittable`/`undefinable`/`derive` — must be called, e.g. `T.always("x")`, since there's no sensible bare default). `T.derive({ to, from })` is not yet a Schema; `.as(resolve)` is what produces one, matching `compute(source).as(resolve)`.
- **`index.ts`** — `export * from` the kind's files, plus `export { default }`.

**The factory's parameter is the kind's `Core`, not its `Schema`.** `Schema()` exists to _attach_ the builder methods, so its parameter has to describe the schema without them, or every caller (including the recursive call inside `adapt`) would have to supply a method it has no way to produce. `Core` is that shape. `object` is the sole variation: `extend`/`refine`/`override`/`adapt` come from `make()` in its `Registry.ts` and so must stay _in_ the parameter, leaving `Omit<Schema<$Definition>, "as">` — omit exactly what the factory adds, which for every other kind is all of the methods and therefore just `Core`.

### Match `Core`, never `Schema`, in a dispatch

`ToTypeBox` and `AsFabricator` must match a kind's `Core`, never its `Schema`. A `Schema` interface's methods are part of its structural shape, and neither a built Fabricator nor a `toSchema`-normalized field entry has them — matching `Schema` instead of `Core` silently falls through to the generic `TSchema`/loose fallback whenever the target interface has a required method (e.g. `.adapt(...)`), with no compile error and no test failure unless something specifically asserts the built shape. `pkg/fabricator-adapter-typebox-v0/test/index.types.test.ts`'s `builtAlways`/`builtComputed` assertions guard this for `always`/`object.compute`.

**Not every kind has a bare form.** `string`/`bigint` have _no_ default `[Meta]` on their Registry export — only `[Kind]`. There is no natural bound to fuzz a string/bigint to, so `T.string` alone is not buildable; it needs `.whereby({...})` first. Building bare `T.string` crashes at `meta.produce` with `meta` being `undefined`. If a schema won't build, check whether its kind actually has a bare form before assuming a bug elsewhere.

## Wiring a new leaf kind into the rest of the system

Adding a primitive is not self-contained inside its own folder. Every one of these needs a matching case/branch, or the new kind silently falls through to a generic fallback (or a `tsc` error via `never(kind)` exhaustiveness checks, which is the good failure mode):

1. `src/Primitive/index.ts` — import, `export { default as <name> }`, add to the `Fabricator`/`Schema` unions (this is also what `Kind` is derived from, so skipping this silently breaks step 4's exhaustiveness check).
2. `src/Fabricator/Types.ts` — `AsFabricator<$Schema>`'s dispatch chain, so `new Fabricator(T.newKind)` resolves to the precise Fabricator type instead of the loose fallback.
3. `src/Fabricator/Constructor.ts` — a `case "newKind":` in `make()`'s switch. For a composite kind, recurse via `make()` again (not `construct()` — see "two-layer dispatch") for any nested schema.
4. `src/Schema/Core.ts` — `violatesKind`'s switch. Enforced by `tsc`: `default: return never(kind)` makes an unhandled kind a compile error. A kind whose values are never checked directly (e.g. `object.compute`, `object.omittable`, `object.optional` — validation happens against the _unwrapped inner_ kind instead) still needs a trivial `return false;` case to satisfy exhaustiveness.
5. `pkg/fabricator-adapter-typebox-v0/src/index.ts` — both `ToTypeBox<$Schema>`'s mapped-type dispatch _and_ the runtime `convert()` switch. Easy to update one and forget the other: only the runtime one has a test that would catch a totally missing case (the type-level one fails silently into `TSchema`).
6. The kind's own three files have to thread `$Adaptations` (`Core`, the `Schema` interface and its factory, the `Fabricator` type) and add `.adapt(...)` — nothing outside the folder enforces this, so a kind that skips it simply can't be adapted, silently. `string` is the reference for a `$Meta`-parameterized kind, `array` for a `$Definition`-parameterized one, `object` for the case where `Registry.ts` owns the builder methods.
7. `src/Enumeration/Plan.ts` — a `case "newKind":` in `axisFor()`'s switch, deciding whether the kind is an **enumerable axis** (a fixed, finite set of outcomes — `enum`, `boolean`, a wrapper's presence outcomes, `choice`'s branches) or **width 1** (everything whose value set is drawn rather than chosen). Enforced by `tsc` the same way `violatesKind` is: the switch is on a `SchemaKind`-annotated local, not the `Resolvable`-typed node, so `default: return never(kind)` makes an unhandled kind a compile error. Width 1 is the safe default — it costs `coverage`/`combinatorial` accuracy, never correctness. A composite kind must also carry `[Children]` (see "Systematic enumeration") or `axisFor` has nothing to recurse into.
8. `pkg/fabricator/src/Primitive/namespace.ts` — add `export * as <name> from "./<name>"` (re-exported from `internal.ts` as `Primitive.<name>`), or no adapter can reach that kind's `Core` type for dispatch.

Then, separately, add representative test coverage:

- `test/Fabrication.types.test.ts` — one representative built Fabricator per primitive, asserting `Fabrication<typeof x>` resolves to the right value type. Compile-time only.
- `pkg/fabricator-adapter-typebox-v0/test/index.types.test.ts` — if the new kind has a TypeBox counterpart worth asserting precisely.
- A dedicated `test/<Feature>.test.ts` for anything with real runtime behavior (see `Compute.test.ts`, `Override.test.ts`, `Omittable.test.ts` for the shape).

### The declaration-emit trap: `tsc --noEmit` passing is not enough

`bun run check`/`tsc --noEmit` only type-checks — it says nothing about whether `bun run build` (which additionally emits `.d.ts` files) will succeed. These are different passes with different failure modes.

The trap: a kind whose `Registry.ts` has a bare, no-call form (`boolean`, `date`, `number`, `symbol`) builds its default export as `export default { ...Schema({...}), otherMethods }` — spreading a `Schema(...)` call directly into the top-level exported object, rather than assigning it a name first. When the declaration emitter emits that module's `.d.ts`, a spread-into-an-object-literal doesn't preserve the spread source's named type (`Schema<$Meta>`) — it structurally re-expands into an anonymous type with every one of `Schema<$Meta>`'s own properties written out individually, `[Produces]` (a symbol-keyed property) included. Printing a symbol-keyed property into a `.d.ts` requires that symbol to be a genuinely-referenced, nameable value at that exact spread site — and if the object literal passed to `Schema(...)` never actually sets `[Produces]` (it's optional, so omitting it type-checks fine under plain `tsc --noEmit`), the emitter has nothing to print a name for and fails declaration emission with:

```
error TS4082: Default export of the module has or is using private name 'Produces'.
```

This applies to _every_ optional symbol-keyed property on `Core`, `[Adaptation]` included, in the same four files (`boolean`/`date`/`number`/`symbol`'s `Registry.ts`). Any future symbol added to `Core` will need the same handling.

Do **not** remove the `[Produces]: undefined as unknown as Fabricated` / `[Adaptation]: {}` assignments at those top-level spread sites — they look like dead code but are load-bearing for declaration emission while staying invisible to `tsc --noEmit` and `bun test`. Keep `[Produces]` (and `[Adaptation]`) genuinely assigned at that top-level spread site specifically: `[Produces]: undefined as unknown as Fabricated` — the double cast (through `unknown`) is only there to satisfy `exactOptionalPropertyTypes` (a bare `undefined` doesn't satisfy `Fabricated`, and `undefined as Fabricated` directly is rejected as a non-overlapping cast); the runtime value is unchanged, still literally `undefined`. Nested spreads within the same file (e.g. `date`'s `past`/`future`, `number`'s `integer`) do **not** need this — only the module's actual top-level default-exported spread does.

After touching any `Registry.ts` that uses this bare-spread pattern, or any change to `exactOptionalPropertyTypes`-adjacent typing, run `bun run build` before considering the change verified — and since both packages' own `check`/`test` scripts require `dist/` to already exist, running `bun run test`/`bun run check` right after will exercise the fresh build's declaration output anyway. `RSDOCTOR=true` is **not** the default: each package's `build` script (`build:reset` → `build:compile` → `build:types` → `build:verify` → `build:clean`) runs plain, with no analytics window and no hang risk, so it's safe as a routine, non-interactive dependency step. Opting into the `@rsdoctor/rspack-plugin` analytics report is a separate, explicit `build:rsdoctor` script (the same chain with `build:compile:rsdoctor` in place of `build:compile`) — reach for it only when a human actually wants the report open in a browser; it is never invoked as a dependency step anywhere in this repo.

### Who emits the `.d.ts`, and why it isn't `tsgo`

Declaration emit does **not** go through Rslib. Every package sets `dts: false` in its `rslib.config.ts` — Rslib emits only `dist/esm` — and a separate `build:types` script emits `dist/types` with the `typescript-5` devDependency (the same npm-aliased TypeScript 5.9 `check:ts5` uses):

```
bun --bun ../../node_modules/typescript-5/lib/tsc.js -p ./tsconfig.build.json --noEmit false --declaration --emitDeclarationOnly --declarationDir ./dist/types
```

This is deliberate, and reverting it will reintroduce a nondeterministic build failure. `rsbuild-plugin-dts` picks its backend from the installed `typescript` version: at 7.x it hard-forces the native `tsgo` executable and rejects `dts.tsgo: false` outright, so as long as the `typescript` devDependency is 7.x, "use Rslib's dts" and "use tsgo" are the same choice.

**The bug:** tsgo 7.0.2's declaration emitter nondeterministically drops named import specifiers from an emitted `.d.ts`. Measured on this repo: **19 of 100 identical emits** of `pkg/fabricator` lost some or all of `import type { Adaptation, Kind, Meta, Produces } from "../../Types"` in `Primitive/number/Types.d.ts`, leaving `Core`'s `[Kind]`/`[Meta]`/`[Produces]`/`[Adaptation]` computed keys unresolvable. Nothing in the source triggers it — same source, same binary, same flags, different output — and it is not the `Meta` shadowing (`Types.ts` locally declaring `export type Meta` while importing the `Meta` symbol): aliasing the import to a non-colliding name still flaked at the same rate, and `string`/`date`/`bigint` shadow identically without ever flaking. TypeScript 5.9 emit is byte-identical to a good tsgo emit except for property ordering in the six bare-form `Registry.d.ts` files, and flaked 0 times in 25 runs.

**How it surfaces:** `skipLibCheck: true` suppresses the errors inside the corrupt `.d.ts` itself, so core's own build stays green and the damage shows up in a _dependent_ package as a bewildering error against untouched code — the reason this reads as an adapter bug when it isn't:

```
[tsgo] src/index.ts:569:22 - error TS7015:
[tsgo] Element implicitly has an 'any' type because index expression is not of type 'number'.
[tsgo] 569       const meta = s[Meta];
```

**The guard:** `build:verify` runs `tsc --noEmit -p ./tsconfig.verify.json` — a third tsconfig per package that includes `./dist/types/**/*.d.ts` and flips `skipLibCheck` back to `false`, type-checking the emitted declarations as ordinary source. It runs between `build:types` and `build:clean` in every package's `build`, so a corrupt emit fails the build instead of shipping: CI's Build workflow uploads `dist/` as the artifact `publish.yml` releases, and a dropped import in a file no dependent happens to reference would otherwise reach npm/JSR silently. Keep it wired in; it costs one `tsc` pass and is the only thing standing between a compiler bug and a broken published `.d.ts`.

## Compound / field-only kinds (`object.compute`, `object.omittable`, `object.optional`)

Some kinds only make sense _as a field inside `T.object(...)`_ — a rule about how that field resolves, not a value on their own. Three exist, all namespaced under `object.*` (`src/Primitive/object/compute/`, `src/Primitive/object/omittable/`, `src/Primitive/object/optional/`) and all following the same shape:

- `Kind` is a dotted string (`"object.compute"`, `"object.omittable"`, `"object.optional"`), not registered as a normal top-level `Kind` union member the way `array`/`string`/etc. are treated by most dispatch sites — but _is_ still a real member of the overall `Kind` union and still needs the full checklist above (`violatesKind` in particular).
- `object/index.ts` re-exports each submodule as a namespace (`export * as compute from "./compute"` / `export * as omittable from "./omittable"` / `export * as optional from "./optional"`), so `Primitive.object.compute` / `Primitive.object.omittable` / `Primitive.object.optional` come along with `import { Primitive }` — no separate import.
- `object/Fabricator.ts`'s fabricate loop special-cases the presence-affecting two via a combined `isObjectOmittableFabricator(v) || isObjectOptionalFabricator(v)` check, handled identically (`Omitted` skips the key; anything else, including `undefined`, is written like any ordinary value) — `object.compute` gets its own separate branch, since it needs the rest of the object fabricated first (two-phase: ordinary fields resolve, then compute fields resolve against them), not a presence decision.
- Both `object/Registry.ts`'s `.override()` and `Adapter/TypeBox`'s `convert()` unwrap to the wrapped field's _own_ kind/schema before doing anything kind-specific with it (`violatesKind` against the inner kind for all three; TypeBox recursion into the inner schema wrapped in `Type.Optional(...)` for `object.omittable`, `Type.Optional(Type.Union([inner, Type.Undefined()]))` for `object.optional`).
- `T.omittable`/`T.optional` are registered as normal top-level `T.omittable(...)`/`T.optional(...)` (via `Primitive/index.ts`'s `export { default as omittable } from "./object/omittable"` and the equivalent for `optional`), even though they live under `object/` and are only meaningful there — `T.compute` is _not_ similarly exposed, since compute fields only ever get minted through `.refine(({ compute }) => ...)`'s closure-scoped `compute`, never called bare.

If a future primitive is "a rule about how an object field behaves" rather than "a value," this is the pattern to reach for, not a bolt-on flag somewhere.

**Contrast with `T.undefinable`** (`src/Primitive/undefinable/`): superficially similar to `T.omittable`/`T.optional` — a factory wrapping one inner schema, a roll on its own private stream, `.as(produce)` / `.weighted(...)` support — but it is _not_ a compound/field-only kind, and does not live under `object/`. The roll decides different things: `T.omittable`/`T.optional` decide whether the _key_ exists at all (a structural fact about the enclosing object, meaningless outside one); `T.undefinable` only ever decides the _value_ itself — either the wrapped value or literally `undefined` — which is an ordinary value usable anywhere a schema is usable (a top-level `new Fabricator(T.undefinable(...))`, an array element, or an object field that stays required but whose value may be `undefined`). Concretely: `T.undefinable` is a normal top-level `Kind` (registered directly in `Primitive/index.ts`, not namespaced as `object.something`); `object/Fabricator.ts`'s fabricate loop needs **no** special-casing for it (an undefinable field's `.fabricate()` result — `$T` or `undefined` — is assigned to `fabricated[k]` exactly like any ordinary field, since a present-and-`undefined` value is the whole point, unlike `Omitted`); and `object/Types.ts`'s `Fabricated`/`Override` types need **no** changes for it either (`ValueOf` already resolves to `$T | undefined` via `ToTypeBox`, and the field stays a required key, never joining `OmittableKeys`). The only place it _does_ need unwrapping like the `object.*` kinds is `object/Registry.ts`'s `.override()` — validating an override value against `undefined | <inner kind>` still needs the inner kind, which `violatesKind` can't see on its own.

**Why `T.optional` isn't `omittable(undefinable(inner))`.** `T.optional` needs a uniform 1/3 split across "omitted," "present as `undefined`," and "present with a value." Composing two independent 50/50 rolls (`omittable` wrapping `undefinable`) gives 50/25/25, not 33/33/33 — so `object/optional/Fabricator.ts` instead does its own dedicated three-way roll via `weighted()` (`Distribution/index.ts`, the same helper `boolean.weighted` uses), picking a `"omitted" | "undefined" | "value"` discriminant and only calling `source.fabricate()` on the `"value"` branch — same as `omittable`/`undefinable`, the wrapped schema's own stream is never touched on the other two outcomes.

## `T.tuple` — fixed arity, one Fabricator per slot

`T.tuple([A, B, C])` (`src/Primitive/tuple/`) is `array`'s heterogeneous, fixed-arity counterpart: exactly N slots, each its own schema, rather than one shape repeated a fuzzed number of times. Standard five-file anatomy, normal top-level `Kind` (not namespaced under `object.*` — an ordinary value, usable anywhere a schema is usable, the same standing as `array`).

**The mechanical distinction from `array`:** `array.Fabricator` is handed a single already-dispatched `element` Fabricator and calls `element.fabricate()` in a loop — every position draws sequentially off _one_ stream. `tuple.Fabricator` is instead handed `elements`, one independently-dispatched Fabricator _per slot_ — the same shape `object`'s fields take, not `array`'s. Concretely, `Constructor.ts`'s `case "tuple":` loops over `[Meta].items` calling `make(item, [...path, String(i)], context)` once per slot, extending `path` by the slot's own index, and passes the resulting array of Fabricators straight through; a bare `tuple` never calls `toStreamFromTrace` itself — its randomness lives entirely on its slots — but it still records `trace` so a nested tuple can be replayed. `.as(produce)` is the exception for both: `produce` needs a stream to hand `ProduceContext.random`, so `toStreamFromTrace` _is_ obtained then.

**`[Meta].items`, not `.definition`**: named after `choice`/`enum` (the other kinds holding a list of items), not the single-schema wrappers (`array`, `undefinable`, …) that use `definition`.

**No `isTupleSchema` guard, unlike the `object.*` kinds.** Those guards exist so `object/Registry.ts`'s `.override()` can unwrap to an inner kind before calling `violatesKind`. `T.tuple` doesn't need unwrapping: an override for a tuple-valued field is wholesale replacement (like `array`), so it's just an ordinary `Override` leaf — `violatesKind(kind, value)`'s generic `"tuple"` case (`!Array.isArray(value)`, arity deliberately unchecked, same rationale as its other coarse-shape-only cases) handles it with no special casing anywhere in `object/Registry.ts`.

**The `Fabricated<$Items>`/`ToTypeBox` trap:** both need to turn `$Items` (a tuple of schemas) into a same-shaped tuple of derived types. A homomorphic mapped type — `{ [$K in keyof $Items]: ... }` — type-checks fine for any _concrete_ tuple, but produces a malformed type for the _default_, unparameterized `$Items = ReadonlyArray<Item>` (the bound a kind-local `Fabrication<$Fabricator>`/`ToTypeBox` resolves against for the bare, unbuilt-generic case): `keyof ReadonlyArray<Item>` pulls in `"length"`/array-method keys too, not just numeric indices — a defect `tsc --noEmit` alone won't surface; only a bare-vs-concrete comparison (`tupleCore.Fabrication<typeof tuple>` in `Fabrication.types.test.ts`) will, via a `.schema.as` contravariance error. Both `tuple/Types.ts`'s `Fabricated` and `Adapter/TypeBox/index.ts`'s `TupleItems` instead use head/tail recursion (`$Items extends readonly [] ? [] : $Items extends readonly [infer $Head, ...infer $Rest] ? [...] : <fallback>`), the exact same shape `ChoiceOptions` already uses for `choice`'s `[weight, option]` pairs — see that type's own doc comment for the full rationale. Don't "simplify" either back to a homomorphic mapped type without a bare-vs-concrete assertion (as `Fabrication.types.test.ts` has) to confirm it's safe.

## `T.derive` — fabricate a value from other schemas' values

`T.derive({ to, from }).as(resolve)` (`src/Primitive/derive/`) produces a value from other schemas' fabricated output without wrapping them in an object. Standard five-file anatomy, normal top-level `Kind`. `from` is a tuple of schemas, fabricated independently like `T.tuple` (one child Fabricator per slot). `Constructor.ts`'s `case "derive":` loops over `[Meta].from` calling `make(item, [...path, "from", i], context)` once per slot — `"from"` then the slot index, so those streams cannot collide with this node's own (which `resolve` draws from) or with each other. `to` is a schema or builder (`T.string`, `T.bigint`) that declares only the result's type and shape, exactly `object.compute`'s `Source` — reused from `object/compute/Types.ts` along with `Denoted`/`Resolved`. Adapters reflect `to` (`recurse(s[Meta].to)` / `ToTypeBox<Denoted<$To>>`); `violatesKind` checks the result against it inside the Fabricator and throws `DeriveResultMismatchError` on a mismatch. The kind checked is `toValueKind(to)` (`Schema/Core.ts`), which follows a `to` that is itself a `derive` or `object.compute` down to a checkable kind.

`.as(resolve)` is required; there is no re-`.as()` on the Schema (matching compute). `resolve(values, { random, clock })` receives `tuple.Fabricated<$From>` and this node's own `ProduceContext`, so extra randomness still replays under a salt. `T.derive` always mints a stream — `resolve` is always present and is handed `ProduceContext`, the same standing as `T.opaque`. Enumeration plans it like `tuple`: each `from` slot is its own axis with a `{ slots }` pin, and `resolve` hands the pinned values to `fabricate({ from })`, which runs `resolve` on them instead of fabricating each slot. That way an enumerable input is still covered. `recursive/Terminate.ts` maps `from` like `tuple` but leaves `to` alone even when it contains `self`: `to` is never dispatched, so it cannot recurse. This differs from compute's `source`, which still throws.

`.override()` checks a derive-valued field against `toValueKind(fieldSchema)`, which is its `to` kind, as it does for a compute field's `source`. Wrapper fields (`nullable`, `optional`, and the rest) resolve their inner schema the same way. `violatesKind`'s `"derive"` case returns `false` only because every caller resolves through `toValueKind` first.

## `T.record` — fuzzed keys, and the two things that makes weird

`T.record(keySchema, valueSchema).whereby({ size })` (`src/Primitive/record/`) is `array`'s keyed sibling: one repeated value shape, a fuzzed count, but entries instead of indices. Standard five-file anatomy, normal top-level `Kind`, mechanically closest to `array` — `Constructor.ts`'s `case "record":` dispatches the key and value schemas _once each_ and hands both to the Fabricator, which reuses them for every entry (contrast `object`/`tuple`, one Fabricator per position). It draws its own size, so unlike `object`/`tuple` it mints a stream (and records `trace` like every other node).

**Keys come from a Schema, not a built-in alphabet.** `record.Key` is `AnySchema & { readonly [Produces]?: string | symbol }` — constrained through the phantom marker rather than by enumerating kinds, so any current or future key-producing kind qualifies and `T.number`/`T.date` are rejected at the call site. This is also what lets a key's `pattern` hint reach TypeBox's `patternProperties`.

**Colliding keys collapse; they are not redrawn.** There is no uniqueness facility anywhere in this library, and a redraw loop would either throw on a seed-dependent schedule or silently cap out. Instead the config says so: `size: { max, minTried? }`. The asymmetry is the documentation — `max` is a real upper bound (collisions only ever shrink), while the lower bound is not guaranteed. Deliberately no bare-number form (unlike `array`'s `length: 3`), since "exactly N" is a promise a collapsing key set can't keep. The count is drawn with the inclusive `min + floor(next() * (max - min + 1))` that `string` and `array` also use — see "Traps in the length/size draw and `trace`."

**Entries are written with `Object.defineProperty`, never `fabricated[k] = v`.** Keys here are _drawn_, so `"__proto__"` is reachable — and bracket-assigning that key mutates the prototype instead of creating a property. `defineProperty` writes a real enumerable own property and leaves `Object.prototype` intact. This does _not_ reuse `object/Fabricator.ts`'s `isPollutionKey` throw: that guard protects developer-written keys, where throwing is actionable, whereas a throw on a drawn key would fire on a seed-dependent schedule — exactly the pseudo-flakiness the testing notes warn about. `Record.test.ts` pins the case with a `T.always("__proto__")` key.

**`Fabricated` splits on open-vs-finite keyspace, not string-vs-symbol.** An open key (`string`, `symbol`, or both) becomes a plain `Record<K, V>` — no `Partial`, since an index signature never guarantees a key is present. A finite literal key set becomes `Partial<Record<K, V>>`, which is honest: the size is drawn and collisions collapse, so a two-member key schema may cover only one. Carrying `ValueOf<$Key>` through the open branch rather than hardcoding `string` is what keeps a mixed `string | symbol` key from silently collapsing to `Record<string, V>`; `Fabrication.types.test.ts` asserts the negative for exactly that.

**Symbol keys throw in the TypeBox adapter.** `TRecordOrObject` has no `TSymbol` branch, so `Type.Record(Type.Symbol(), v)` returns `TNever` (`{"not":{}}`) — a schema nothing validates against, produced without raising. The runtime `convert()` therefore tests the _result_ for `Never` (which catches every unrepresentable key shape, not just symbols, and survives TypeBox adding or removing a branch) and throws. The type level needs no guard: `TNever` is honest there, and `Static<TNever>` is `never`. `.adapt(typebox, ...)` is the way out. Two related surprises: symbol keys are invisible to `JSON.stringify`/`Object.entries`, and a symbol-keyed object trivially _passes_ a `Record(String, V)` check.

**No `.override()` special-casing needed.** A `record`-valued field is an ordinary `Override` leaf — wholesale replacement like `array`/`tuple` — validated by `violatesKind`'s coarse `!isPlainObject(value)`. That holds only because `record.Core` carries the phantom `[Produces]`; omitting it would silently degrade the whole override to `unknown`.

## `T.opaque` — the escape hatch, and the one kind with no non-`produce` path

`T.opaque(produce)` (`src/Primitive/opaque/`) fabricates a value this library has no kind for — a `Map`, `Set`, `URL`, `RegExp`, `Uint8Array`, class instance, branded type. `Fabricated<$T> = $T`, inferred from `produce`'s return type, so `T.opaque(({ random }) => new Map<string, number>())` needs no annotation.

**Why it exists, given `always`/`enum` already hold arbitrary values.** `T.always(someMap)` types correctly but hands back the _same reference_ on every call and has no `.as()`. `T.enum.uniform([...]).as(produce)` can technically produce a fresh value per call, but only by passing a throwaway member purely to satisfy the type and discarding it — `T.opaque` is the direct way to express "fabricate a fresh value of a kind this library has no primitive for."

**Every kind's `produce` — `T.opaque`'s constructor argument and every other kind's `.as(produce)` alike — takes one argument, a `ProduceContext` (`Random/Types.ts` — `{ random, clock }`).** `random` is the schema's own seeded `Stream`; `clock` is the construction's resolved "now," in epoch milliseconds (see "Randomness"). `Stream` is public for this reason (`src/index.ts` re-exports the type) — it is `random`'s type, so a caller writing the producer as a named function needs to name it. `test/Opaque.test.ts`'s replay assertion is `T.opaque`'s own guard on this; it fails if the stream is ever swapped for an unseeded source. Reading `random`/`clock` is opt-in everywhere except `T.opaque`, where the producer's logic _is_ the entire value, so it needs the stream directly; an ordinary kind's `.as(produce)` can ignore `ProduceContext` entirely (e.g. calling an unseeded library like faker), which is what puts that call outside the seeded-reproducibility guarantee — tolerable there, since `.as()` overrides a kind that otherwise draws properly on its own.

**`T.opaque` is the one kind with no non-`produce` path at all — it always mints a stream.** Every other kind's `Fabricator(...)` calls `toStreamFromTrace` only inside its `if (meta.produce)` branch (or the equivalent drawing path) — the bare/default path never needs a stream. `T.opaque` has no bare path to fall back to: `meta.produce` is always present, so it always obtains a stream. Don't "optimize" the always-true `if (meta.produce)` check away — the branch structure is what every other kind's own conditional stream minting mirrors. `.trace` is recorded on every kind unconditionally; opaque is special only in always _minting_.

**No `.as()`**, for `always`'s reason: the constructor argument already fully determines production. `.adapt()` matters more here than anywhere else, since the default TypeBox mapping is maximally imprecise.

**TypeBox maps it to `Type.Unknown()`, deliberately _not_ a throw** — the opposite call to `record`'s symbol key a few lines up in the same switch, and the difference is the point. There, `Type.Record` _silently_ returns a `TNever` nothing could satisfy, so failing loudly is strictly better than the alternative. Here `Unknown` is an accurate statement about a value the adapter genuinely cannot constrain, and throwing would break `toTypeBox` for any schema merely _containing_ an opaque field — defeating the purpose of an escape hatch.

## Traps in the length/size draw and `trace`

These aren't self-evident from reading the code in isolation — each is guarded by a dedicated regression test, since nothing else in the type system or a casual read would catch a regression here.

- **`array`'s `whereby.length.min` must be honored, not just `max`.** Exclusive ends are resolved first (`effectiveDiscrete` in `Bound.ts`) into an inclusive integer interval, then the length draw is `min + Math.floor(stream.next() * (max - min + 1))` — the same formula `string` and `record` use for their size draws. A spec without an explicit `min` canonicalizes to inclusive `0`, so an empty array is a legitimate outcome. `test/Array.test.ts` pins this.
- **Call-site `min`/`max` scalars are inclusive; a stored end is always `{ value, exclusive }`.** `.whereby()` runs `toBound()`. Adapters read that shape: TypeBox uses `minimum`/`exclusiveMinimum` for value bounds (the stated value, not the discrete interior) and `minLength`/`minItems` via `effectiveDiscrete` (length has no exclusive JSON-Schema keyword). `T.date` exclusive ends also go through `effectiveDiscrete` on epoch milliseconds — `Date` is `TimeClip`'d, so a continuous ulp nudge of a float ms still constructs as the excluded instant. `test/Date.test.ts` pins this. Bare `T.number` / `T.number.integer` carry no `whereby`; an omitted `.whereby()` end stays omitted (not a default of `0`). Fabricate fills `±Number.MAX_VALUE` / `±Number.MAX_SAFE_INTEGER` for the missing end. `sampler` maps a unit draw with `(1 - u) * min + u * max`, never `min + u * (max - min)` — that subtraction overflows to `Infinity` at `±Number.MAX_VALUE` (and any equally wide pair).
- **Unbounded `T.number.integer` must still be whole** — it uses the same discrete floor path as a bounded integer. `test/Integer.test.ts` pins this.
- **`encode(trace)` is five elements** — every `Trace` slot, nothing else — so `toStream(algorithm, encode(trace)).seed === stream.seed` has no carve-out. `deriveClock`'s two-element encoding stays trivially distinct from five.

If you touch the length/size draw, note the formula is shared in spirit by three kinds (`string`, `array`, `record`) — diverging one of them from the others is a regression, not a local fix.

## Randomness — the part that's easy to reason about wrong

A leaf's private stream is keyed by two independent things, resolved at two different times. Conflating them is the usual mistake.

**Once per construction: resolve its construction-owned trace slots.** `RandomSource.toConstructionTrace(pins?)` (`src/Random/index.ts`) runs _once_ per construction, inside `Constructor.ts`'s `construct()`, before any leaf dispatches. It returns a plain `ConstructionTrace` (`salt`, `clock`, `ordinal`) that every leaf spreads into its own `Trace` before `toStreamFromTrace`. Its one stateful decision is the construction-owned `ordinal`: a pinned `ordinal` (`ConstructorOptions.ordinal`) is taken verbatim without bumping the counter — that is what makes a replay exact, and what `combinatorial`/`coverage` rely on by pinning `ordinal: null` next to their derived salt — `null` rather than an omitted key because pins count by definedness, so only a defined "no ordinal" survives a replay (and `toConstructionTrace` checks `!== undefined`, never `??`, which would treat `null` as missing and bump the counter); otherwise it takes the next value from this `RandomSource`'s one construction counter. `fork`/`wrap` each instantiate a fresh source and therefore a fresh counter; `T.recursive` expansions call `toConstructionTrace()` on their private fork. No separate tag records how an ordinal was resolved: `null` itself says "no ordinal", and a replay needs no flag beyond the ordinal itself.

**Once per leaf, within that construction: `toStreamFromTrace(algorithm, trace)`.** `trace` is `toConstructionTrace()`'s result plus this leaf's `path`/`kind`. Derivation is a free function of `(algorithm, trace)` — not a `RandomSource` member — because it depends on no per-source state (`fork` shares only the algorithm). `toConstructionTrace` fixes salt/clock/ordinal before the trace is ever hashed. `construct()` and `recursive/Fabricator.ts`'s `fabricateAt` each resolve the `ConstructionTrace` once and close over it in the `toTrace` they hand down through `ConstructionContext`. Re-resolving per leaf would bump the construction counter on every field (dispatch-order sensitivity). `path` is structural position — field name, tuple slot, choice option index — threaded through `make(schema, path, context)` and extended by one segment per composite (`object` appends the field key; `tuple`/`choice` append the slot/option index as a string; `array`/`record`/presence wrappers append `"element"`/`"key"`/`"value"`/`"definition"`). The stream is `encode(trace)` hashed directly (`Random/index.ts`) — no key stream, counter, or cache. Invariant: `toStream(algorithm, encode(trace)).seed === stream.seed`. A leaf's path already uniquely identifies it in its construction, so call order does not disambiguate. Inserting, removing, or reordering a sibling changes that sibling's path and nothing else's (`test/StructuralKeying.test.ts`).

**`[Fixed]` does not dispatch for stream-parity.** `case "object":` still `make()`s an overridden field before discarding the result, but only to see via the built `[Kind]` whether it was `object.compute` (see `[Fixed]`). Skipping that dispatch cannot shift any sibling's stream — there is no shared counter left to skip.

`new Fabricator(schema, { salt })` (`resolveScope`, `ConstructorOptions` in `Random/Types.ts`) pins the `salt` slot of the construction's `Trace` — one option among `clock`/`ordinal`, not a special case. **It does not fork.** A bare salt replaces the instance salt for that build, `layer(...)` composes onto `base.salt`, and every other slot resolves exactly as it would have: next ordinal from this source's counter. So a salted build shifts and is shifted by its neighbours like any other, and is **not** position- or clock-independent. Isolation (own counters) is `fork`/`wrap`; an `ordinal` pin is for builds that must not advance the source counter (`combinatorial`/`coverage` pin `ordinal: null`). A replayed `Trace` whose `clock` is present explicitly is: `ConstructorOptions` accepts every `Trace` slot (`salt`, `clock`, `path`, `kind`, `ordinal`), `Trace` is assignable to it, and `new Fabricator(schema, trace)` is a legal replay. A given `ordinal` is taken verbatim with no counter bump. Two instances reproduce an identical explicitly-salted build only if they also agree on clock; the unconfigured default is a wall-clock instant captured at `initialize()`, so two such instances in different milliseconds diverge even on `{ salt }`, unless both pass the same explicit `clock` or `clock: "derived"`. Reproducible _and_ varying with the instance salt means a separate instance salted from the parent, not a construction salt — `ConstructorOptions` has nothing for that besides `salt: layer(...)`. No per-build algorithm override either: `initialize({ algorithm })` already covers bringing your own PRNG.

**Fabricate-time.** After dispatch, `.fabricate()` draws from that leaf's `Stream` only. Sibling streams are already separate generators. A conditional inner draw (`object.omittable` skipping the value) only advances _that_ leaf's stream on the next call to the same built Fabricator.

**`.trace`** on a built Fabricator is the `Trace` that node's stream was hashed from — recorded on every node, whether or not it minted a stream. Slots, in encode order: `salt` (the _instance_ salt), `clock` (construction "now," epoch ms), `path`, `kind`, `ordinal` (which construction on this source — counted, pinned, or `null` for a `combinatorial`/`coverage` build). No `iteration` (no counter to report) and no derived-salt field (`encode(trace)` recovers it). `.trace.clock` is never `undefined` — clock is resolved before any leaf dispatches. `new Fabricator(schema, trace)` replays the node; compute / `recursive.self` / `[Fixed]` still need the parent (see `test/Trace.test.ts`).

**The trace is the reproducibility unit, not `salt` alone.** The stream salt is `encode(trace)`, the whole tuple. An omitted slot cannot be accounted for. `clock` sits second, after `salt`, because both are instance-level and perturb every leaf; later slots narrow. `Config.clock` is `number | "derived"`: an explicit `Date` and the unconfigured wall-clock default collapse to epoch ms at `overlay()` and are inherited; `"derived"` stays a sentinel through every `overlay()` (`fork`/`wrap` included) so it re-derives when the composed salt changes. Eager resolve would freeze a `"derived"` fork's clock against the parent's salt while `initialize()` with the same composed salt derives a different one. `resolveClock(config)` is the only collapse of `"derived"`: `instantiate` needs a concrete `Options.clock` (`deriveClock` draws from a throwaway stream `JSON.stringify([salt, "clock"])`, kept below `RandomSource` — a fork's clock is an input to stream derivation, so deriving clock from a fork would be circular), and `context.clock` re-resolves on every read (the active `wrap` frame can change). Drawing kinds read `trace.clock`, which reaches kind logic (`date` past/future) and every `.as(produce)` via `ProduceContext.clock`.

**Wrapping integrations.** A library that calls `new Fabricator(...)` for the user shares the instance's construction counter unless it partitions its work. A single construction can use `new Fabricator(schema, { salt: layer(identity) })` so it still varies with the instance salt; a block of work is better isolated with `instance.fork({ salt: layer(identity) })` or `instance.wrap({ salt: layer(identity) }, block)`, both of which own fresh counters. A bare `ConstructorOptions.salt` replaces the base salt and does not isolate the counter. `src/Harnessing/` is this pattern applied per test; see "Harnessing integration".

## `fork` — deriving a layered instance

`instance.fork(overlay?)` (`src/Instance/`) derives a new `Instance` over the one `fork` was called on: named fields override, omitted fields inherit. A full peer of `initialize()`, including its own `fork`.

**`src/Instance/` exists so `initialize()`'s body is extractable.** `Instance/Types.ts`: `Config` (fully resolved — every field present, what `overlay()` always produces); `Overlay` (`Partial<Omit<Config, "salt" | "clock">>` plus `salt` that also accepts `Layered`, and `clock?: Date | "derived" | undefined` in caller form, not `Config`'s `number | "derived"`); `Instance` itself (re-exported unchanged from `src/index.ts`). `Instance/Core.ts`: `overlay(base, over): Config` and `instantiate(config): Instance` — the shared body of `initialize` and `fork`.

**`overlay()` is the only inheritance site.** `base` is `Partial<Config<PlainObject>>` so both callers use it: `initialize(config)` is `instantiate(overlay({}, config ?? {}))`; `fork` overlays the instance it was called on (already a full `Config`). `salt` composes only when tagged `layer(...)` (`isLayered`) — `[...normalizeSalt(base.salt), ...normalizeSalt(over.salt[Layer])]` — else a bare `salt` replaces, an omitted one inherits, and at the root (no base salt) the mixer is empty unless an env var supplies one (`normalizeSalt(undefined)`). Wall-clock `clock` is the default entropy; `salt` is an optional mixer. `algorithm`/`types` replace wholesale when given, else `?? base.X`, falling back to the built-in algorithm/default registry only at the root; no deep merge (`registry.extend(...)` already does that). `limits` is re-validated via `resolveCombinatorialLimit` on every `overlay()` (given, inherited, or defaulted) so a bad limit fails at `fork()`/`initialize()`, not first `combinatorial(...)`. `clock` follows given → inherited → default like `algorithm`, but stays _unresolved_ only for the explicit `"derived"` sentinel: an explicit `Date` and the unconfigured wall-clock default become epoch ms and are inherited; `"derived"` stays the sentinel so `fork({ salt: layer(...) })` re-derives from the composed salt. `resolveClock` collapses `"derived"` at read time (see "Randomness").

## `wrap` — ambience, and why `fork` is taught first

**Editorial constraint, not just a preference: the docs lead with `fork` and present `wrap` as sugar for when the scope cannot reach the code that needs it.** A fork is a configuration held as a value, so every receiver means exactly itself. Inside a `wrap` a receiver does **not** tell you which configuration a call draws from — the instance `wrap` was called on and that instance's ancestors are affected, which is precisely what makes a destructured `Fabricator` work. State that plainly wherever it comes up; do not apologise for it or imply it is a defect. `docs/src/pages/guides/reproducibility.mdx`'s "When you cannot thread the scope: wrap" and `harness.mdx`'s "Why this one uses `wrap`" carry this; keep them aligned if either moves.

**Do not re-propose "only the root instance is ambient."** It looks like it removes the misleading receiver, and it does — but "root" is an accident of where `initialize()` was called, not a statement about how an instance is used. A caller may `fork` an application-wide config, hand the fork to `integration(...)`, destructure `Fabricator` off it, and never name the original again; under that rule the harness's per-test `wrap` stops reaching them and per-test partitioning dies silently. The handed-in fork is the receiver, so it is reached; forks _of_ it are not. Pinned from both directions: `test/Harnessing.test.ts` (non-root instance handed to `integration()`) and `test/Wrap.test.ts` (a fork treated as its own root). The misleading receiver is inherent to ambience — a call's config comes from dynamic context rather than its receiver — so it is settled by documentation, not by API.

**`instance.root` is identity only.** Every instance carries it, a root naming itself, so nothing handles absence. `a.root === b.root` answers "same lineage?" and is the public replacement for reading `ancestry[0]`; `Token` is therefore **not** exported (`Ancestry` still is, since public `Stack.visible` names it). Carried on `instantiate`'s `parent` object and exposed as a getter returning `parent?.root ?? instance` — the same forward reference `context.scope()` relies on. It is not an ambient accessor and not "the configuration to prefer": `root`'s config is where the lineage started, not what is in effect. **Typed at `PlainObject` as a shortcut, not a necessity** — do not repeat the old comment's claim that a fork makes the root's registry "different", which is false: a root's registry is fixed at `initialize` and `fork({ types })` mints a new instance without touching it. What is lost is recoverability — after such a fork the descendant's `$Registry` is the fork's — and regaining it would mean threading `Instance<$Registry, $Root>` through `fork`/`wrap`, rejected as a poor trade for an identity accessor. `context.scope()` is the genuinely-unknowable case, since it depends on which instance entered the visible frame.

`instance.wrap(overlay, block)` is `fork(overlay)` ambient for the synchronous extent of `block`: every `new Fabricator(...)`, `combinatorial(...)`, and `coverage(...)` inside — on this instance, and on this instance's ancestors — resolves against the fork with nothing threaded through. A descendant (a fork of the receiver, or the wrap's own scope) draws the configuration it was built with. `block` also receives the fork as `scope`, for explicit use and for anything that must survive past `block`'s first `await`.

Descendants are excluded so a fork of a wrap's scope keeps its own layer, a fork created before the wrap is not silently overridden, and a later wrap does not steal a fork's layer (`test/Wrap.test.ts`). The accepted cost under the harness: per-test data comes from the integrated instance, `context.fabricator`, or a fork of that scope — never from a module-level fork of the integrated instance (`test/Harnessing.test.ts`).

**The carrier holds a chain; `Ancestry` decides who may read it.** Created once at root `initialize()`, threaded through every descendant `fork`/`wrap`, never re-created. `Stack` is `{ asynchronous, visible(ancestry): ReadonlyArray<Frame>, enter(frame, block) }`; `enter` **appends** to the open chain (nested wraps remain a chain) and unwinds in a `finally` so a throw still pops. `initialize()` calls `toStack()` once and passes it into `instantiate(config, stack)`; `instantiate` threads that reference _and_ the instance's `ancestry` into every `Constructor(source, stack, ancestry)` and `enumerables(source, limits, stack, ancestry)`, and recursive `instantiate` from `fork`/`wrap` passes the stack through while extending the ancestry.

**`Ancestry` is a chain of opaque per-instance `Token`s, receiver-derived.** `instantiate(config, stack, parent?)` mints a `Symbol` (`mint()`, brand key module-private to `Instance/Types.ts`, so a token cannot be forged) and appends it to `parent.ancestry`; `parent`'s absence is the **single** marker of a root. `parent` is `{ ancestry, root }` as one optional object rather than two optional parameters, because the two always travel together — a derived instance has both, a root has neither — so they cannot drift into disagreement. Keeping `parent.ancestry` at the non-empty `Ancestry` is also what lets `[...parent.ancestry, mint()]` stay assignable with no cast: a possibly-empty chain (a root passing `[]`) guarantees nothing about position 0 and fails `TS2322`. The local `ancestry` it builds is this instance's — the parent's plus one. `ancestry[0]` is where lineage identity physically lives (`instance.root` is the public handle for asking about it), so identity is the instance's rather than the carrier's, and two `initialize()` calls handed the _same_ `stack` still cannot see each other's frames. `initialize({ stack })` is purely a choice of carrier. Both `fork` and `wrap` extend from the **receiver**, matching how `config` now inherits, so position and configuration never disagree about who the parent is.

**Which frames a call can resolve against is a prefix test in one direction** (`governs`, `Instance/Stack/Visible.ts`): the reader's chain a prefix of the wrap's receiver — the reader is the receiver or one of its ancestors. Descendants, siblings, cousins, and unrelated lineages never. Do not restate this as "common ancestry" or as a bidirectional "direct line": siblings share every token up to their parent and any two instances in a lineage share `ancestry[0]`, so those relations admit precisely the pairs this test rejects. `toVisible(frames, ancestry)` **filters** rather than walking in from the innermost frame and stopping at the first that does not govern the reader, because a governing frame can sit beneath one that does not: with `B`'s `wrap` open and `C`'s nested inside it, `B` must pass over `C`'s frame and still resolve against its own. A stop-at-first variant passes every other ambience test, so that case is pinned on its own. `toInnermostFrame(stack, ancestry)` is the last element, and the single definition every consumer goes through. Both carriers delegate filtering here so the rule cannot drift between them. Guards: `test/Wrap.test.ts` — sibling isolation, ancestors not descendants, a parent's wrap not reaching its children, skipping a non-governing frame, shared-carrier isolation, and ancestry shape.

**A `Frame` is `{ config, source, instance, ancestry }`, storing the scope's already-built `RandomSource` rather than just `Config`.** `fork` and `wrap` share one `derive(over)` helper — `overlay(config, over)` then `instantiate` — so both lay over the instance they were called on and cannot drift apart on what they inherit from. `wrap` therefore **writes** the stack and never reads it; every read lives in `resolveScope`, `effectiveSource`, and the `context` getters. The frame's `ancestry` is the **origin's** (the receiver), not the scope's. That is **not** what decides who is governed: keyed on the scope, a frame governs the same instances plus the scope itself, and the scope resolves against the frame's own `source` either way. The only observable difference is `context.depth` — keyed on the origin, a scope reads 0 inside its own wrap; keyed on the scope it would read 1, and an ancestor governed by a later wrap on that scope would count one more. Do not describe the key as "the rule". `instance` is kept for `context.scope()`. Then `derive(wrapOverlay)` once, and push its `config`/`source`/`instance` alongside the origin's `ancestry` — reuse that `source`, don't derive a second. Implicit (`Fabricator`/`combinatorial`/`coverage` via `toInnermostFrame`) and explicit (`scope.Fabricator`) therefore share one `RandomSource` and one set of construction-ordinal counters; independently re-deriving from `scopedConfig` would silently diverge. Guard: `test/Wrap.test.ts`'s first test (interleave implicit/explicit, compare against a sequence built entirely through `scope`).

**`resolveScope` is the only place a construction consults the ambient frame.** It calls `toInnermostFrame(stack, ancestry)` fresh every call — not when the `Constructor` closure was built — so the same `Fabricator`/`combinatorial`/`coverage` reference behaves differently inside a `wrap` it can see. `base` is that frame's `source` if there is one, else the instance `source`. **Unsalted** takes the next ordinal on `base` (a no-op for `scope.Fabricator` because `frame.source` already _is_ that instance's source). **Bare salt** pins `normalizeSalt(given)` into the trace, still on `base`, still the next ordinal — no fork. **Layered salt** pins `[...base.salt, ...given]`, resolved against whichever base is in effect — the one interaction between construction-level `layer(...)` and an active `wrap` (`test/Wrap.test.ts` both directions).

**`enumerables` needs the same override and cannot reuse `resolveScope`:** `combinatorial`/`coverage` derive `[...base.salt, "combinatorial"]` (etc.) _before_ `new Fabricator(...)`, so the frame must be read then. `effectiveSource()` (`toInnermostFrame(stack, ancestry)?.source ?? source`) is called fresh inside `combinatorial(schema)`/`coverage(schema)` — those bodies run on every caller invoke, never cached — so the same `combinatorial` reference enumerates differently inside a `wrap` this instance can see. The explicit `{ salt }` they pass still wins over `resolveScope`'s frame lookup; the accompanying `ordinal: null` pin leaves the source's construction counter untouched.

**`context` is a live view (getters), not a snapshot.** `context.salt`/`.algorithm` read `(visibleFrame()?.config ?? config)` at access time — a `context` captured before a `wrap` still reflects it while active and reverts after. Same `toInnermostFrame(...) ?? ...` path as `resolveScope`, so there is one definition of "config in effect now." `context.scope()` returns that frame's own `instance` (else this one) — the explicit way to compose against whatever is active, and what replaced `wrap`'s old implicit frame-overlay; `context.depth` is `stack.visible(ancestry).length`, so it counts only frames _governing this instance_. A wrap's own scope is a descendant of the receiver, so its depth inside that wrap is 0 — it already holds the wrap's configuration as its own. **`scope` is a function, not a fifth getter, and that is load-bearing:** it is the one member acted through rather than read, so a destructured getter would freeze into correct-looking code laying over the wrong base, where a frozen scalar is merely a visibly stale value. As a function it captures the lookup and survives destructuring (`test/Wrap.test.ts` pins both halves). Like the getters it names `instance`, declared below it — legal because its body runs only when called. `context.clock` cannot read the field directly: it calls `resolveClock(...)` because the frame's `Config.clock` may still be `"derived"`. `wrap({ clock: someDate })` overrides ambient clock for the block like `wrap({ salt })`; an omitted `clock` on a wrap whose composed salt differs from its base keeps a captured/explicit instant and re-derives only under `"derived"`, same as `fork`.

**The ambient carrier is selected by package condition, and `wrap` refuses an async block when it cannot carry one.** `Stack` (`Instance/Types.ts`) is public and declares `asynchronous`; two implementations live in `Instance/Stack/`, and the `#stack` subpath import in `package.json` picks between them. `node`/`bun` resolve to `Async.ts` (`AsyncLocalStorage`) through `dist/`, `deno` resolves to the same file through `src/` — `dist/` is gitignored and never reaches the JSR tarball, which is what that separate condition is for, and the built output additionally loses the `node:` prefix (rslib rewrites it to a bare `async_hooks`, which Node and Bun accept and Deno does not). Everything else falls to `default`, `Sync.ts`, the original LIFO. `Async.ts` is the **only** module in the package importing `node:` anything; keep it that way, or the package stops loading where there is no `node:async_hooks`. On an ALS carrier a frame survives `await` and concurrent `wrap`s stay isolated, so the old "synchronous extent" rule no longer applies there. On the sync carrier it still would, so `wrap` throws `FabricatorError.SynchronousStackError` the moment `block` returns a thenable rather than letting a later build resolve against the base instance unannounced — thrown synchronously, after neutering the abandoned promise with `then(noop, noop)` so it cannot also surface as an unhandled rejection. That rejection is deliberately coarse: it fires even when `block` only ever touches `scope`, because whether a later build reads the ambient frame is not knowable from `wrap`. `initialize({ stack })` overrides the choice, and `toSynchronousStack` (`internal.ts`) is how the suite reaches the sync carrier at all, since Bun always resolves to ALS. Guards: `test/Wrap.test.ts` — frame-survives-`await`, the async twin of the shared-source invariant, concurrent isolation, and both synchronous-carrier cases.

## Harnessing integration (`src/Harnessing/`)

`integration(instance)` (`Harnessing/Core.ts`) decorates an existing `Instance` as a `@ghostry/harness` integration, `{ name, provides, frame }`. It takes an instance rather than minting one so the caller owns `initialize(...)`, and in particular the suite-wide `clock`.

**`wrap` is the seam, and the receiver is `context.scope()`.** `frame` yields a wrapper that is `instance.context.scope().wrap({ salt: layer(saltFor(identity)) })`; `body` is handed to `wrap` directly rather than called inside a closure, since `wrap(overlay, block)` already takes `(scope) => $Return`, which is exactly the wrapper's own `(established) => $Return`, so the scope `wrap` opens _is_ the established value with nothing in between to adapt it. Each `wrap` re-instantiates, so every test gets a fresh construction counter: ordinals are per test, and `.only`, filters, shards, and `.concurrent` cannot shift a neighbor's data. That is the order-independence property — no execution counter exists anywhere. `layer` composes onto the frame in effect, so `initialize({ salt })`/`FABRICATOR_SALT` still vary the whole suite.

**Overlaying `instance` instead would drop an enclosing scope, silently.** That receiver is bound before any test runs, so an integration composed _inside_ another library's fabricator scope — `@ghostry/extern`'s fabricator extension opens one around every testing block — would restate from the configured instance, discarding the enclosing layer while still landing innermost and therefore governing every draw (`resolveScope` takes the innermost frame's source, not the constructing instance's). `context.scope()` is the frame in effect, or the instance itself when there is none, so one expression covers both with no branch. Splicing `context.salt` into a bare overlay reaches the same composed value and is **not** the way: it bypasses `overlay` and hand-rolls `layer()`. The per-test wrap therefore governs `context.scope()` and that instance's ancestors — the integrated instance, and an enclosing scope's instance when something else wrapped first — never forks of the integrated instance. Per-test data must come from the instance handed to `integration(...)`, `context.fabricator`, or a fork of that scope. `test/Harnessing.test.ts` pins the composed salt, that fork consequence, and clock inheritance through the frame.

**`saltFor` (`Harnessing/Salt.ts`) is `[kind, ...path, name, row?]` and carries no file.** Per-test `wrap` already partitions constructions more finely than a file would, so a file segment would only subdivide a partition whose blast radius is one test — and leaving it out means `Identity` holds nothing a wrapper cannot know at registration, so `@ghostry/harness` never walks a stack. The accepted cost: same-path tests in different files share a salt. `kind` leads because `name` is `""` for both a suite identity and a test a user names `""`, and `path` never carries a leaf's own name; without `kind` those two collide. Two suite identities at one path (a `beforeAll` and an `afterAll` in one `describe`) do share a salt, intentionally. No version or namespace segment: a `Trace` replays verbatim and is never re-derived, so there is nothing a version would guard.

**`frame`, not `setup`.** The ambient frame must enclose the body, and only a wrapper does. `frame` is a generator with one suspension point, which is what lets `yield` be both where the body runs and where the hook waits: everything before it is setup, and what it carries is the wrapper the body runs inside. There is nothing after the `yield` — fabricator has no teardown, and the ALS carrier keeps the frame across `await` regardless. On the sync carrier an async body raises `SynchronousStackError` from `wrap`. Declaring no `setup` also keeps harness on its uninstrumented path, where a synchronous assertion failure is reported at the user's own line.

**`provides.fabricator` returns what the wrapper established, not a closure slot.** The yielded `Wrapper` hands the scope `wrap` opened to the body, and harness hands that same value to every provider as `ProviderArgs.established` — so the scoped instance travels from wrapper to provider directly, with nothing written on the way in and read on the way out. That is what makes it safe under `.concurrent` without reasoning about interleaving at all. A provider reached with no established scope is a composer running providers outside the frame it opened, and raises `FabricatorError.HarnessingProviderError` rather than quietly returning the base instance.

**Nothing here sets `clock`.** It reads `instance.context` for `scope()` alone. A pinned `Date` and the wall-clock default are epoch ms by the time `overlay()` sees them, so they inherit through every per-test `wrap` — including from the frame in effect, so a caller who wrapped a different instant around a group of tests gets that instant inside them rather than having the per-test scope revert to the instance's own. `"derived"` re-derives per test, and that is left alone: the policy's meaning is that the salt is the reproducibility unit.

**The contract is a structural copy, not an import** (`Harnessing/Types.ts`) — the arrangement `Adapter`/`walk` use. `Integration` is the subset of harness's contract this integration uses: no `setup`, and `frame` required here though optional there. `Frame` is narrower in the same way — only the synchronous generator, where harness accepts an `AsyncGenerator` too; the narrower satisfies the wider, and declaring the async arm would invite an integration that promotes every test in a suite to a promise for no reason. Both hooks take a single object — `FrameArgs` for `frame`, `ProviderArgs` (the same thing plus `established`) for a provider — so a field added to the contract later is a key an existing hook ignores rather than a parameter it has to thread past. `Provides` is homomorphic over the context type, so the contributed keys are read off `provides` itself; harness rejects a key collision across integrations from `Object.keys(provides)`.

**The runtime tests never use the real `@ghostry/harness`; the type check does.** `test/fixtures/harnessingConsumer.ts` stands in for its composer — outside-in, each `frame` run to its `yield` first, the yielded wrapper applied around everything inner, every provider run inside that wrapper and handed what it established — and is the contract's executable specification, so the two repos have no build-order coupling. Nothing about a structural copy otherwise checks that the two still agree, which is what `test/Harnessing.conformance.test.ts` is for: `@ghostry/harness` is a **devDependency** — never a `dependency` or a `peerDependency` — and that file asserts assignability in the one direction that matters, what `integration()` builds against what harness's `initialize()` accepts. A consumer installs neither it nor that file; the `files` allowlist ships `dist` alone. `test/Harnessing.test.ts` pins the salt properties and the scope handoff; `test/Harnessing.types.test.ts` pins the types. The entry adds no external runtime import, so `test/Platform.test.ts` passes unmodified.

## `ValueOf`'s `$Bindings` — the mechanism `T.recursive` closes the loop with

`ValueOf<$Schema, $Bindings>` threads a **substitution slot for a self-reference** — not a parameter of the schema the way `$Definition`/`$Value` are — and every **composite** kind's `Core` is an `interface` (not a `type` alias) carrying an optional `bindings?: unknown[]`, forwarding `NonNullable<this["bindings"]>` into its own `[Produces]` without ever reading what's in it. Named `$Bindings` rather than TypeBox's own `Params` (the mechanism is a direct port of `Static<T, P> = (T & { params: P })['static']`) because "params" reads as configuration, and this is closer to a de-Bruijn-style resolution environment. Kept as a tuple, as TypeBox's is, so a second bound self-reference could occupy index 1 later without restructuring — though nothing today defines what that would mean.

It exists so a schema node whose `[Produces]` reads `bindings[0]` — `recursive.self.Core`, the analogue of TypeBox's `TThis` — can close a type-level fixed point: `recursive.Types.ts`'s `RecursiveValue<$B> = ValueOf<$B, [RecursiveValue<$B>]>` resolves instead of collapsing to `unknown`. That self-referential alias is normally `TS2456`; it is legal only because the recursion routes through an **interface member lookup**, which is the entire reason the `Core`s must not be type aliases.

`test/ValueOfBindings.types.test.ts` is the only thing asserting the threading mechanism in isolation, and it is load-bearing: reverting a single composite `Core` to a `type` alias silently breaks threading for that kind alone, with no other test noticing (verified — reverting `nullable` fails exactly the two assertions that depend on it).

Three details in `ValueOf` itself each look simplifiable and are not — see its own doc comment for the full reasoning: **indexed access, not conditional `infer`** (the `infer` form fails `TS2615`); **`Required<>`, never `Exclude<…, undefined>`** (`Exclude` strips the legitimate `undefined` from `nullish`/`undefinable`/`object.optional`/`undefined`); and **the `extends` guard inside rather than as a parameter constraint** (constraining forces `[Produces]` onto `AnySchema`, which shifts variance and breaks `.as`'s contravariant check).

Leaf kinds are deliberately untouched — they never read bindings, so they stay `type` aliases. `AnySchema` is untouched too, and `[Produces]` stays optional, so the phantom contract and the declaration-emit trap are unaffected.

## `T.recursive` — trees, and the one place dispatch happens lazily

`T.recursive((self) => body).whereby({ depth: { max } })` — trees, linked structures, a generic JSON value. Without it, every compound kind normalizes eagerly (`toSchema`, at construction) and `Constructor.ts` walks the whole schema tree eagerly (at `new Fabricator(...)`), so nothing can reference itself — manual nesting works exactly one level deep (the children have no children).

**`T.recursive(body)` is a builder, not a Schema** — `.whereby({...})` is what produces one, matching `array`/`record`/`string`; no bare form. `body` is called exactly once, eagerly, with a single freshly-minted `self` placeholder (`recursive.self.Core`) — the same timing `array`/`record` already normalize their own nested definitions at call time, not deferred to `.whereby()`.

**`self` lives under `recursive/self/`, namespaced the same way `object.compute` is under `object/`** — `[Kind]` is the dotted string `"recursive.self"`, not a normal top-level `Kind` union member the way `array`/`string`/etc. are treated by most dispatch sites, but it is still a real member of the overall `Kind` union and needs the full "wiring a new leaf kind" checklist. `recursive/index.ts` re-exports it as a namespace (`export * as self from "./self"`), so `Primitive.recursive.self` comes along with `import { Primitive }` — no separate import, mirroring `object/index.ts`'s `export * as compute from "./compute"`.

**The value type is inferred, with no annotation, to arbitrary depth** — `recursive.Types.ts`'s `RecursiveValue<$Body>`, described in the `$Bindings` section above. `test/Recursive.types.test.ts` is what would catch a regression back to `unknown`/`any`.

**`self` is not exposed as `T.self`** — like `object.compute`, it's only ever reached through the closure `T.recursive` hands its body. `Constructor.ts`'s `make` and the TypeBox adapter's `convert` both match it only by `[Kind]`, never by identity, so a `self` reference captured out of its own callback and reused elsewhere doesn't silently do something wrong — it throws (`test/Recursive.test.ts` and the TypeBox test file both cover this exact misuse).

**Termination is derived from `body` when `terminal` is omitted** (`recursive/Terminate.ts`), and an explicit `terminal` lives in `.whereby(...)` rather than a second argument to `T.recursive(...)` on purpose: `terminal` sits exactly where a recursive value was expected, so `ValueOf<$Terminal>` must be assignable to `RecursiveValue<$Body>` — as a second argument to the same call, `$Body` and `$Terminal` would infer together, making that constraint circular. Split across the builder, `$Body` is already fixed by the time `.whereby()` runs, so the check is ordinary structural assignability (verified with a bare-vs-generic comparison — a fixed field type rejects a wrong `terminal` identically to making it its own type parameter, so `recursive.Core` doesn't need to remember `$Terminal`'s type at all once it's checked). Derivation rewrites every `self` behind a declining kind into a stop (empty `array`/`record` via a fresh `opaque` collection, remaining non-`self` `choice` arms, `null`/`undefined`/`Omitted` for presence wrappers) so the result contains no `recursive.self` nodes — `Constructor.ts`'s `make` still dispatches nested schemas eagerly, and `recursive.self` throws when `context.self` is missing at the ceiling. A required `self` (object field, tuple slot, naked body, or a `choice` with no remaining arm) throws `UnterminableRecursiveError` at `.whereby()`. A provided `terminal` is a wholesale override of that derivation, not a patch of `self` sites. `depth.max` is a ceiling on an emergent quantity, not a bound on a drawn one — `fabricateAt` only compares a counter against it, and realized depth is decided by whichever kinds sit between `self` occurrences declining to recurse (an `array`/`record` rolling a count of 0, a `choice` picking a non-`self` option, an `omittable`/`optional`/`undefinable` resolving absent). So `depth` has no `min` the way `array`/`record`'s genuinely constrains a _drawn_ count; a real floor would mean coercing those intervening kinds' own draws, not adding a second number here. The derived terminal may empty a collection whose `body` said `length.min > 0`: the ceiling has to stop somehow.

**A hand-written `terminal` that empties a collection field needs `T.opaque(() => [])`, not `T.always([])`.** The terminal needs an empty array typed as the _same_ element type the recursive field uses, but that type isn't nameable while the schema is still being defined. `T.always([])` types fine but hands back the **same array reference to every leaf** — a live mutation hazard `test/Recursive.test.ts` asserts against directly (no two leaves that terminated in the same `fabricate()` call share a `children` array). Derived terminals already use a fresh empty collection per leaf.

### The runtime: the one place dispatch happens inside `fabricate()`, not before it

Every other kind's dispatch count is a pure function of its schema shape, decided once at `new Fabricator(...)` time. A recursive schema's isn't — how deep any given `fabricate()` call goes depends on prior random draws (an array's own length) made _during_ that same call — so expansion has to happen lazily, inside `fabricate()`, one `self` occurrence at a time. `recursive/Fabricator.ts`'s own doc comment has the full reasoning; two things about it are worth knowing before touching that file:

- **Isolation, not memoization.** Dispatch count is data-dependent, so no structural path distinguishes sibling expansions at the same depth (an `array` of three `self` children calls `fabricateAt` three times on one shared element Fabricator; unlike a tuple slot index, the schema does not tell them apart). Dispatching against the instance `source` would let that random depth perturb the next unrelated Fabricator from the same `initialize()`. Replay of the same salt and clock through the same `fabricate()` sequence already reproduces the node's own results — isolation is for everything else. The node gets a private `RandomSource.fork(salt)` from its draw, and each `fabricateAt` resolves a `ConstructionTrace` on it (`toConstructionTrace()`). The private source's construction counter orders expansions; no ordinal to keep by hand. Guard: `test/Recursive.test.ts` — an unrelated Fabricator from the same instance is unaffected by how many times the recursive schema fabricated first.
- **No file-threading needed.** Expansion does not depend on the call stack — a counted scope resolves without walking it — so there is nothing to capture at build time and thread down; each `fabricateAt` call's `context: ConstructionContext` is built fresh from the private source's own scope, with `path` reset to `[]` beneath it (structural position inside `body`/`terminal` is only meaningful relative to one expansion, not to this node's own outer position).

Every `self` occurrence gets its own independently-dispatched expansion — calling the bound resolver twice (e.g. two array slots) triggers two separate `fabricateAt` calls, each opening its own scope and so drawing from its own independent stream space — the same convention `tuple` already uses for its own slots (each independent) rather than `array`'s single-shared-element convention. This is what gives sibling branches of a tree independent randomness instead of a correlated shared sequence.

Both `Constructor.ts`'s `make` and the TypeBox adapter's `convert` take an optional context parameter (`ConstructionContext` / `BuildContext`) threaded through _every_ recursive call so it reaches however deeply a `self` node sits nested — only `case "recursive"`/`case "recursive.self"` in each read its contents; every other branch just forwards it unchanged. If you add a new composite kind, remember to propagate it.

**TypeBox needs none of the isolation problem** — building a schema draws no randomness — so its side is far simpler: `Type.Recursive((This) => build(body, { self: This }))`. `terminal` is never separately built: `Type.Recursive` already produces a `$ref`-based schema whose validation naturally recurses however deep an actual value goes, and a terminal-shaped leaf is just an ordinary instance of the same shape with its self-referencing fields empty/absent.

A doubly-recursive body (`left: self, right: self`) costs 2^depth, so `depth.max` should stay small (3–4) — worth saying in user-facing docs, not just here.

## Systematic enumeration — `combinatorial` and `coverage`

`initialize()` returns two more functions besides `Fabricator`: `combinatorial(schema)` enumerates every combination of every enumerable node as a cartesian product; `coverage(schema)` enumerates the minimum set where every option of every enumerable node appears at least once. Both take a Schema, both return a lazy, re-iterable `Iterable`. Implementation lives in `src/Enumeration/` — `Types.ts` (type aliases only), `Plan.ts` (the untyped, `Random`-free walker), `Enumerate.ts` (the one typed boundary, mirroring `Constructor.ts`'s own `make`/`construct` split).

**It walks the _built_ tree, not the Schema — via `[Children]` — and pins by driving the existing `fabricate(overrides)` path.** `Constructor.ts` already dispatches every nested Fabricator (`object`'s fields, `tuple`'s slots, `derive`'s `from` slots, `choice`'s options, each wrapper's inner) but keeps them closed over privately; `[Children]` exposes exactly those already-dispatched Fabricators, so `Plan.ts` can recurse over the same tree `Constructor.ts` built rather than re-deriving anything from `[Meta]` alone. Enumerating then means building the schema **once** and, for each combination, calling `built.fabricate(overridesFor(combination), { validate: false })` — which is what makes three things fall out for free rather than needing separate handling: the two-phase `object.compute` resolution (computed fields simply stay out of the override map and resolve normally against the pinned result); `Omitted` forcing a presence-wrapper field off (it is already a valid override value, per `object/Fabricator.ts`); and every non-pinned field still drawing its own randomness per instance, so the parts you didn't enumerate stay properly fuzzed.

**Every `.weighted(...)` treats `0` as disabling that outcome.** Negative weights, `NaN`, and `Infinity` still throw `InvalidWeightError` at construction; an empty drawable set (every remaining weight zero) throws `NoDrawableOutcomesError`. `weighted()` (`Distribution/index.ts`) already filters `!isDrawable` entries out of its draw table, so fabricate-time needs no per-kind change. `axisFor` (`Enumeration/Plan.ts`) is weight-aware: it filters through `isDrawable` / `drawableOutcomes` rather than treating the declared branch set as the fabricable set — without that, `coverage()` would pin a value `fabricate()` can never produce. Both guards live in `Distribution/index.ts` beside `weighted()` itself, so the rule can't drift from the filter it mirrors: `assertDrawableWeights` for the caller-supplied `[weight, item]` lists (`enum`/`choice`'s registries), `assertDrawableKeyedWeights` for the fixed, named outcome sets (`boolean`'s `true`/`false`; `nullable`/`nullish`/`undefinable`/`object.omittable`/`object.optional`'s presence outcomes — each in that kind's `Schema.ts`).

Per-entry validity is `isValidWeight` (`weight >= 0 && Number.isFinite(weight)`), distinct from `isDrawable` (`weight > 0`). `NaN >= 0` is `false`, so `NaN` is rejected without a separate comparison. For the keyed form, an explicitly-`undefined` value means "unspecified" (falling back to the baseline `1`) and is skipped in the per-entry check. Zeroing a named outcome changes the _distribution_, not the _type_: `T.optional(x).weighted({ omitted: 0 })` still types the key as optional. A narrower kind is still how you change the type.

The TypeBox adapter is not weight-aware: a zeroed outcome leaves the adapted schema _wider_ than the fabricable set (`Type.Boolean()` still validates both booleans; `Type.Optional` still validates an always-present key). Every fabricated value continues to pass `Value.Check`, so this is precision, not correctness. Narrowing would need either weights in the type (the keyed kinds' `.weighted()` discards them) or a runtime/type-level divergence this codebase avoids.

**Sum vs product is the rule that makes `coverage` minimal _and_ correct.** `choice` and every presence wrapper (`nullable`/`nullish`/`undefinable`/`object.omittable`/`object.optional`) are **sum** nodes: only one branch is realized per instance, so their widths **add**, in both `combinatorial`'s `"product"` strategy and `coverage`'s `"cycle"` strategy — `choice([enum3, enum2])` is a 5-wide axis, not `max(3,2)=3`, because a max-3 schedule would make two of the five outcomes structurally unreachable. `object` and `tuple` are **product** nodes: every child is realized in _every_ instance, so under `"cycle"` they collapse to the **widest** child's width (narrower children cycle/reuse their options), while under `"product"` they multiply as an ordinary cartesian product. "Cycling" — the option-reuse behavior — is therefore a product-node-only concept; a sum node never repeats an option.

**Three width-1 guards, checked in `Plan.ts`'s `axisFor` before any per-kind logic**, and the first is correctness, not an optimization: `[Meta].produce` present (from `.as()`) makes the value set opaque, since every kind's `Fabricator.ts` short-circuits on it before any schema-driven logic runs; `[Fixed]` on an `object` field (from `.override()`) — read off the **parent's** `[Meta].definition`, since the built field itself no longer carries `[Fixed]` — must collapse that field to width 1 or the enumerator would silently discard the user's override; and an `object.compute` field is excluded from the pin **entirely** (not even as a width-1 entry), since it is derived in `object/Fabricator.ts`'s phase 2 and is never a valid override target.

**`coverage`'s `"cycle"` strategy needs a per-axis _permutation_, not merely a phase offset, or equal-width axes lock in lockstep.** A naive `i % width` starts every axis at index 0, so two axes of the same width are either always equal or always locked to one fixed relationship — concretely, any two `T.boolean` fields would be either always-equal or always-opposite on every single run, since their index difference is constant regardless of a constant offset. `Plan.ts`'s `plan()` (the thin wrapper around the per-kind `axisFor` dispatch) fixes this by drawing a fresh Fisher–Yates permutation of `0..width-1` for **every** width→1 node it visits (sum nodes included — a sum axis handed an out-of-range index by an enclosing cycling product still needs to self-normalize), via an `Orderer` built once in `Enumerate.ts` and threaded through as data. The coverage guarantee survives regardless of the permutation: instance count is the widest axis, so a narrower axis of width `w` is visited at that many _consecutive_ positions mod `w`, and a permutation is just a bijective relabeling of which value sits at which position — never fewer than all `w` of them get covered.

**Repeatability comes from `new Fabricator(schema, { salt })`, isolation from the `ordinal: null` pin passed with it — no enumeration-specific machinery.** Each of `combinatorial`/`coverage` derives one salt from `source.salt` (e.g. `[...source.salt, "combinatorial"]` — `Enumeration/Enumerate.ts`) and rebuilds fresh **every `[Symbol.iterator]()`**, not at call time — so a second pass gets new streams instead of continuing the first. The salt pins each rebuild to the same universe; the `ordinal: null` pin leaves instance construction counters untouched (a salt alone does not). `coverage`'s permutation stream is a second independent fork off the same derived salt, rebuilt alongside the Fabricator on every iterator.

**Widths are counted in `bigint`, not `number`, so `combinatorial`'s limit error states an exact count.** A product of many axes can exceed `Number.MAX_SAFE_INTEGER`, where `number` would silently go imprecise and eventually report `Infinity` — the limit comparison itself would still be decided correctly, but the count in the thrown message would be a lie. `bigint` literals (`5n`) don't compile under this project's `ES2019` target; write `BigInt(5)`, as `bigint/Fabricator.ts` already does. `combinatorial`'s check is eager — it builds once, reads the axis width, and throws before producing anything if it exceeds `limits.combinatorial` (validated at `initialize()` time, not first call). `coverage` carries no limit at all: its count is the widest single axis, which can never exceed the schema as written, so there is nothing for a limit to protect against.

## Two-layer dispatch (appears twice, similar shape both times)

Both `Fabricator/Constructor.ts` and `Adapter/TypeBox/index.ts` split their work into an untyped recursive core plus exactly one precisely-typed boundary that casts once at the edge: `Constructor.ts`'s `make()`/`construct()`, and `Adapter/TypeBox/index.ts`'s `convert()`/`toTypeBox()`. Both untyped cores switch on runtime `[Kind]`, and neither typed boundary is ever called from within its own core — there's no reason to re-pay the type-level dispatch for a schema you already know is buildable.

The two untyped cores recurse differently. `Constructor.ts`'s `make` calls _itself_ again for nested schemas (an `object` field, `array` element, `choice` option), extending `path` by one segment each time; the `ConstructionTrace` was resolved once before `make` recurses. `Adapter/TypeBox/index.ts`'s `convert` never calls itself: it recurses through a `Recurse` callback handed in by `Adapter/Core.ts`'s `walk` (see "Adapting to an external schema library"), so every nested node passes back through the adaptation lookup exactly as the root does.

## Override mechanisms (two, and they compose)

1. **Schema-baked**: `schema.override({...})` (`object/Registry.ts`) — pure Schema → Schema, produces a _new_ Schema with `[Fixed]` values baked into the named fields' entries. Building that new Schema later makes those fields permanently return the fixed value (still fully dispatched first — see `[Fixed]`).
2. **Per-call**: `fabricator.fabricate({...})` (`object/Fabricator.ts`) — a lightweight override on an _already-built_ Fabricator, for one call only, using that Fabricator's own already-drawn randomness for every other field (never a fresh draw). Validates by delegating to `schema.override(...)` and throwing away the result (`{ validate: false }` skips this). Does _not_ go through `[Fixed]`/`Constructor.ts` at all — it directly writes into the loop's `fabricated` object, which is exactly why `Omitted`-as-override-value needs handling in _both_ places independently (`object/Registry.ts` for the baked path, `object/Fabricator.ts` for the per-call path) — they don't share code.

## Adapting to an external schema library

`toTypeBox` maps each kind to one fixed TypeBox counterpart. When that mapping is wrong for a particular schema (a `string` that is really an email, a `date` that has to cross the wire as an ISO string), `schema.adapt(typebox, (schema) => ...)` overrides it.

**An adapter is a value, not a name this package knows** (`Adapter/Types.ts`'s `Adapter` — `{ key, convert }`). Nothing registers anywhere: the adapter is imported at both ends, `.adapt(typebox, fn)` to attach an override and the adapter's own `toTypeBox(schema)` to convert. Core therefore names no external schema library and depends on none; `src/adapting.ts` exports the contract an adapter is built from (`Adapter`, `Recurse`, `walk`, `Adaptation`, `AdaptationsOf`) as its own entry point, separate from `.` — implementing an adapter is a different audience from using one, and `Adapting` (the one piece an ordinary `.adapt()` caller needs) stays on `.` alone despite the name overlap.

- **The write is a per-kind builder method**, not a free helper in the adapter module. Only the method can return _that kind's own_ `Schema<..., WithAdaptations<...>>`, which is what makes the adaptation survive a subsequent `.as()`/`.whereby()`/`.extend()` at the type level. A free helper `adapt(schema, adapter, fn)` doesn't work: knowing only `Buildable`, the best it can return is an intersection, whose carried-over methods still return the _original_ instantiation — so the next chained call drops the adaptation from the type while the runtime spread keeps it, the one direction worth avoiding.
- **`produce` takes one argument, `Adapting<$Schema>` — `{ schema, meta }`** (`Adapter/Types.ts`, re-exported publicly from `src/index.ts` so a caller writing the producer as a named function can name its parameter, the same rationale as `Stream` for `T.opaque`). `meta` is derived by indexed access off `$Schema` rather than named as a second type parameter, so no kind states its own `Meta` twice in an `adapt` signature. The point of the pair is that neither half is reachable only through a well-known symbol: `Kind`/`Meta` are exported from `internal.ts` alone, and an adaptation deriving from its kind's own config is an ordinary caller's business, not an adapter author's. `meta`'s shape is **readable but not stabilized** — a kind stays free to restructure its `[Meta]`, and nothing outside a kind's own files should _interpret_ another kind's. A kind with no bare form carries no `[Meta]` at runtime until configured (`string`/`bigint`), so `meta` can be `undefined` there despite the type, the same imprecision `Schema<$Meta>` already states.
- **The caller-facing producer and the stored adaptation are deliberately different shapes.** What lands in `[Adaptation]` stays schema-taking (`SchemaAdaptation`, `(schema: any) => unknown`); `Adapter/Core.ts`'s `toSchemaAdaptation` wraps a caller's `Adapting` producer into that form inside `withAdaptations`/`mergeAdaptations` — where a producer _enters_ the mechanism, never where one is called. That is what lets `patched`/`layer` keep passing exactly one kind of function around: an incoming producer and a prior already-layered entry stay the same type, and `AdaptationEntry`'s `(schema: any) => $Returnable` stays an accurate account of what a schema carries (asserted directly by `Adapt.types.test.ts`'s hand-written `CarryingForeignOnly` map). It also means `meta` is read at call time off whichever schema `layer` hands down, so a producer sees the current config after a chained `.as()`/`.extend()` rather than one closed over at `.adapt(...)` time.
- **`$Returnable` is inferred from `produce`'s return position, never from a constraint on the argument.** The latter resolves the parameter to its constraint and degrades to an entry no adapter's dispatch matches. Bounding `$Returnable` by `ReturnType<$Adapter["convert"]>` is what makes a producer returning something its adapter could never emit fail at the call site — the reason the adapter is passed rather than named, and something no string key could give.
- **The key is the adapter's own, read off the value as a literal type** (`"@ghostry/fabricator-typebox/v0"`). Two adapters never collide, adapters for two versions of one library coexist on a single schema, and naming the wrong one is an import error rather than an entry nothing looks up. Versioned in the key itself for that reason. `Adaptations` is correspondingly an open `Record<string, (schema: any) => unknown>`, so nothing about a third party's adapter has to be declared here — and it is not a weak type, so no `.adapt(...)` anywhere needs a cast.
- **A computed key in an object literal widens to a `string` index signature**, which no adapter's literal-keyed dispatch matches — so `withAdaptations`/`mergeAdaptations` take `(adapter, produce)` and build the entry through `Adapter/Core.ts`'s `Entry<$Adapter, $Returnable>` mapped type rather than accepting a prebuilt map.
- **`walk` and `layer` are two halves of one mechanism, both in `Adapter/Core.ts`.** `walk` walks a schema with an adapter, checking `[Adaptation][adapter.key]` _before_ the adapter's own per-kind dispatch, and hands the adapter a `Recurse` callback rather than letting it recurse privately — so every nested node (an `object` field, `array` element, `choice` option) gets the same lookup as the root. `layer` is why re-entry terminates: an adaptation is called with the schema it is adapting rewritten to carry whichever adaptation it replaced — absent at the bottom of the stack — so `toTypeBox(schema)` _inside_ an adaptation resolves to the previous layer, or to the kind's ordinary mapping, which is what makes `Type.Intersect([toTypeBox(schema), extra])` work. A schema holds one adaptation per adapter, so without that substitution there is no stack to pop. `layer` operates purely on the stored, schema-taking form; the substituted schema it builds is what `toSchemaAdaptation` later splits into a producer's `{ schema, meta }`, which is why the two halves always describe the same layer.
- **`Recurse<$Context, $Returnable>` carries the adapter's own returnable type**, so a nested result drops straight into a composite the adapter is assembling (`Type.Array(recurse(element, context))`) with no cast at any call site. `$Context` is likewise adapter-private — TypeBox's is the enclosing `T.recursive`'s `This` placeholder.
- **Three places have to stay lossless** for an adaptation to survive: `toSchema` (`Schema/Core.ts`, which every `object`/`array`/wrapper field is normalized through), each kind's `Fabricator` rehydrating `.schema` (via `Schema({ ...schema })`, not a fresh `{ [Kind], [Meta] }` literal), and `object`'s `rehydrate` (`object/Registry.ts`, which also fixes `.override()` on a nested adapted `object` field). `Constructor.ts`'s typed `construct()` boundary re-attaches the map onto the outermost built Fabricator; nested fields need nothing, since adapters read `[Meta].definition`, never the internal per-field Fabricators.
- **`object` is the one kind whose `adapt` lives in `Registry.ts`**, beside `extend`/`refine`/`override` — those rebuild via `make()` rather than deriving from the current schema object, so `make` threads the map explicitly. A map left only on the object would be dropped by the next chained call. `Adapter/Core.ts` exposes `mergeAdaptations` (map level) for exactly this, alongside `withAdaptations` (schema level) every other kind uses; both take `(adapter, produce)`.
- **`[Meta]` storage was considered and rejected.** It would ride every existing spread for free, but kinds parameterized by `$Definition` rather than `$Meta` compute their `[Meta]` type from the definition, leaving nowhere for the adaptation's _type_ to live across `.extend()`/`.refine()` — runtime keeps it, type drops it. It would also break `[Meta]`'s kind-private boundary.
- **`AdaptationsOf` reads the map, always in two steps** (`$Schema extends { [Adaptation]?: infer $Adapter extends Adaptations } ? $Adapter : {}`, then match `Record<Key, ...>` on the result). Matching `{ [Adaptation]?: Record<Key, ...> }` directly is a trap: a conditional matching an optional property against a schema that lacks it entirely still _succeeds_ with an unconstrained `infer` (the same behavior `ValueOf` relies on for `[Produces]`), so every unadapted schema would resolve to the adaptation branch.
- **`Static<ToTypeBox<S>>` and `ValueOf<S>` may legitimately disagree.** That is the feature — you have told TypeBox something the fabricator doesn't honor — and keeping the two compatible is the caller's business. This is not the only source of that divergence. Three others exist, none involving an adaptation: a widened `always`/`enum` over a value TypeBox can only type-approximate (see below); a `record` over a finite literal key set, where `TRecordOrObject` collapses to a `TObject` marking every property **required** while `Fabricated` is `Partial` (a record's size is drawn and colliding keys collapse, so it may cover only a subset); and an `opaque`, whose `Static<TUnknown>` is `unknown` while `ValueOf` is the producer's precise return type. Only the last of those _widens_ rather than conflicts, so it is the one that is safe by construction.

## `always`/`enum` hold any value — and what that costs the adapter

`always.Value` and `enum.Item` are both `unknown` — not capped to `string | number | boolean`, which would just be TypeBox's `TLiteralValue` leaking into the primitive. Narrowing back down to what a given external library can express is that library's adapter's job. What still separates the two kinds: an `enum` draws one of these exact _values_, a `choice` draws one of these _schemas_ and fabricates from it.

Consequences:

- **`violatesKind`'s `always`/`enum` cases return `false`** (`Schema/Core.ts`), joining `choice`. This function receives only `(kind, value)`, never `[Meta]`, so it can never compare against the actual value or member set — it can only assert coarse JS-type shape, which an `enum` of strings would fail for a numeric value anyway.
- **`Adapter/TypeBox`'s `toConst` is deliberately not a bare `Type.Const` call.** `Type.Const` picks the right TypeBox _type_ for any value but stops there, so `Type.Const(5n)` is a bare `TBigInt` accepting any bigint. Where TypeBox has an option bag, `toConst` pins the value back down: `minimum`/`maximum` (bigint), `minimumTimestamp`/`maximumTimestamp` (date), `min`/`maxByteLength` (Uint8Array). It recurses through plain objects and arrays itself rather than delegating, so a pinnable value _nested_ in one gets pinned too — otherwise `T.always({ at: new Date(0) })` would pin nothing while `T.always(new Date(0))` pinned exactly.
- **That recursion must keep mirroring `Type.Const`'s structure**, readonly marking included — object property _values_ wrapped in `Type.Readonly` while the key modifier is stripped (`TFromProperties` maps with `-readonly`), arrays as `Readonly(Tuple(...))`. Otherwise the runtime output drifts from the type-level `ToConst`, which is a plain `TConst`. `Always.test.ts` asserts the two agree by `JSON.stringify` comparison.
- **Runtime pinning is invisible to `Static<>`.** `Static<TBigInt>` is `bigint` whether or not `minimum`/`maximum` are set, because TypeBox has no literal bigint/date/symbol type. So `toTypeBox(T.always(5n))` _validates_ exactly `5n` but its static type is `bigint` — the second divergence source noted above. `.adapt(typebox, ...)` is the escape hatch when the static type matters too.
- **Two things stay genuinely unpinnable**: a `symbol` (TypeBox's `Symbol(options?)` takes no value constraint) and a `Uint8Array`'s _contents_ (only byte length is expressible). Asserted explicitly in `Always.test.ts` so the boundary isn't later mistaken for a bug.
- **`ToConst`'s `unknown extends $Value` guard is load-bearing.** `TConst<unknown>` resolves to `TObject<{}>`, not `TSchema`, so without it a bare, unparameterized `always.Core` claims to be an empty object type instead of falling back to the loose `TSchema`. Same class of trap as `tuple`'s `TupleItems`, and guarded the same way — a bare-vs-concrete assertion in `pkg/fabricator-adapter-typebox-v0/test/index.types.test.ts`.
- **`enum`'s type-level mapping is exact because `enum` is parameterized by `$Items` (the tuple), not `$Item` (the member union).** Mapping through the member union alone can't recover the member count, so it can't distinguish a single-member `TLiteral` from the `TUnion<[...]>` the runtime emits for 2+ members. `enum.Types.ts` keeps `Items` as a real tuple of `[weight, item]` pairs, exactly as `choice.Items` does, and `Adapter/TypeBox`'s `EnumOptions` head/tail-recurses over it into a same-length tuple of each member's `ToConst<...>`, handed to TypeBox's own `Union<T>` so the single-member collapse to a bare `TLiteral` is reproduced too. `EnumOptions` is a near-copy of `ChoiceOptions` and differs only in mapping each member through `ToConst` (members are _values_) rather than recursing into `ToTypeBox` (options are _schemas_) — so `ChoiceOptions`'s doc comment on why head/tail recursion is required and a homomorphic mapped type is not is the authority for both, and both are guarded by bare-vs-concrete assertions in `pkg/fabricator-adapter-typebox-v0/test/index.types.test.ts`. `enum/Registry.ts`'s `uniform` uses the identical tuple-preserving `Weighted<$Items>` mapped type `choice/Registry.ts` does.
- Bigint **literals (`5n`) don't compile** — `target` is `ES2019`. Use `BigInt(5)`, as `bigint/Fabricator.ts` already does throughout.

## Merge semantics: two depths, two purposes

- **`deepMerge`** (`Utility/DeepMerge.ts`) — used by the top-level registry's `T.extend(({ T }) => ({...}))`. Recursively merges nested plain objects (so extending one primitive's namespace doesn't clobber unrelated sibling keys).
- **`shallowMerge`** (`Utility/ShallowMerge.ts`) — used by an `object` schema's `.extend()`/`.refine()`. One level only: a new field entry replaces an old one of the same key wholesale, it doesn't merge into it.
- Both respect the `[Replace]` directive (`replace(value)` from `Utility/Core.ts`) to force wholesale replacement even where the default behavior would otherwise merge.
- `mergeableKeys` carries symbol keys through a merge unconditionally (so a Schema's `[Kind]`/`[Meta]` identity survives extension) but still guards string keys against prototype pollution (`__proto__`, `constructor`, `prototype`).

## The faker extension (`pkg/fabricator-extension-faker-v10`)

Mirrors `@faker-js/faker`'s data modules as `T.faker.*` builders that draw from **fabricator's** seeding rather than faker's own. It is an _extension_, not an adapter (see "Package layout"): `fakerExtension(options)` returns a `registry.extend` callback, so it arrives through exactly the same `deepMerge` path a user's own `registry.extend(({ T }) => ...)` does, and composes with further `.extend()` calls in either order.

### The bridge is one mutable slot (`src/index.ts`)

`let scope: ProduceContext | undefined` — the context of the leaf currently being fabricated, and the whole mechanism. Faker's two configurable inputs both read through it, so they can never disagree about which fabrication they are serving: a `Randomizer` whose `next()` is `current().random.next()`, and `setDefaultRefDate(() => new Date(current().clock))`. **One slot, not one per concern**, because `random` and `clock` always arrive together on a single `ProduceContext` — which is what a kind's single-argument `produce` buys here.

Both are wired **once, at `Faker` construction**, never re-pushed per draw. `setDefaultRefDate` takes a `() => Date` _source_, so a `wrap({ clock }, ...)` active at fabricate time is picked up through `current()` with nothing to re-register — the reason `T.faker.date.past()` and core's `T.date.past` always agree on "now" within one schema.

Every builder wraps its faker call in `draw(produce)`, which **saves and restores** `scope` rather than assigning it bare: a faker method taking a user callback that itself reaches a nested `fabricate()` must unwind to _this_ leaf's scope, not to "none". `current()` throwing `FakerExtensionError.NoActiveScopeError` when the slot is empty is what catches a builder invoked outside `fabricate()`. **The whole save/restore approach is sound only because faker is synchronous** and a producer runs synchronously inside `fabricate()`; it handles nesting and nothing handles interleaving, so an async faker method on a future major is a re-examination, not a tweak.

`Randomizer.seed` is deliberately **inert** (`() => {}`). `new Faker(...)` seeds its randomizer during construction and `faker.seed(...)` is reachable through `use`; honoring either would put a second salt in competition with fabricator's, which is the bug this package exists to remove. For the same reason `Options` accepts no `salt` and no reference date, and **cannot accept a pre-built `Faker`** — a pre-built instance's randomizer is fixed at construction, so it has no route to the stream. `create: (randomizer) => Faker` is the honest form of that escape: the caller builds the instance, this package still supplies the randomizer.

### The mirror is written out, not generated (`src/FakerModules/`)

**Two hand-maintained files, kept in agreement by the compiler.** `FakerModules/Types.ts` declares `FakerModules` — one literal property declaration per builder; `FakerModules/Build.ts` implements it — one expression per builder, under a `build(...): FakerModules` return annotation. That annotation is the whole mechanism: an entry present in one file and not the other, or returning a different kind than declared, is a compile error. Neither file may be edited alone, and there is **no cast anywhere in the construction path** — `src/Construct.ts` is a spread of `build(...)` and an inline `use` hatch, under a `FakerExtension` return type.

There is no code generator and no runtime probe. `Honest<...>` (below) compares every entry against faker's own declared return type, so a method mapped to the wrong kind is a compile error whether a human or a script chose it. A generator would buy labour at the cost of a script to understand, committed output that reads as source but must never be hand-edited, and two hand-filled exception dictionaries covering what a `typeof` probe cannot see.

**Bumping faker is a `tsc` worklist, not a regeneration.** Run `bun run check` and work the errors: `_ModulesExhaustive` names an added/removed module, `MethodsExhaustive<$M>` names a module whose method set moved, `ModuleHonest<$M>` names one whose return types moved. Fix each in both files. The 6 enum member lists are literals (a generator could have read `Object.values(Aircraft)`); `Honest<...>` is what catches a stale one.

### Construction is eager and plain, never a `Proxy` (`src/Construct.ts`)

The namespace is a plain nested object built once, at `fakerExtension(...)` time. A `Proxy` would be actively wrong here, not merely slower: `isPlainObject` is a `proto === Object.prototype || null` check, so a `Proxy` over `{}` **passes** it — `registry.extend` would then traverse it with `Object.keys` and destructively re-copy it into a dead, empty object. (Module classes are also minified in faker's published bundle, so no `constructor.name` heuristic is trustworthy either.)

**Every node is either a plain object or a leaf builder function — never a function carrying properties.** This is the invariant the whole namespace preserves, and it is what keeps any level reachable by a later `.extend()`: `deepMerge` recurses only where `isPlainObject` holds on _both_ sides, so a callable-with-properties is a node that silently swallows an extension aimed into it. It is why a split node exposes `T.faker.color.rgb.text()` with **no bare `T.faker.color.rgb()`**, and why `use` is a namespace rather than a callable. `test/Mergeable.test.ts` walks the namespace asserting it directly; keep it whenever the namespace's shape grows.

### The deviation policy — three rules, in priority order

The mirror is deliberately **not** 1:1 with faker, and each departure is what lets every builder return a real core kind instead of `opaque` (which would convert to `Type.Unknown()` in any adapter and count as width 1 in `Enumeration/Plan.ts`):

1. **Mirror faker's data modules; drop its utility belt.** `helpers` is omitted entirely — core already expresses all of it, and better: `arrayElement`/`objectKey`/`objectValue`/`enumValue` are `T.enum.uniform`, `weightedArrayElement` is `T.enum.weighted`, `arrayElements`/`multiple` are `T.array(...).whereby({ length })`, `maybe` is `T.optional`/`T.omittable`/`T.undefinable`, `rangeToNumber` is `T.number.whereby({ min, max })`. Eleven of its eighteen are generic and would erase to `unknown` anyway. Core overlap _elsewhere_ (`datatype.boolean`, `number.int`, `string.alpha`) is **kept** — those generate data.
2. **Split a method whose return type depends on its arguments.** The 7 `color.*` methods (`rgb`, `cmyk`, `hsl`, `hwb`, `lab`, `lch`, `colorByCSSColorSpace`) return `string` _or_ `number[]` by `options.format`, so each becomes a `{ text, channels }` pair. Channels are `T.array(T.number)`, **not `T.tuple`**: arity is option-dependent (`includeAlpha` adds one; `cmyk` has 4 where the rest have 3), so a fixed arity would be wrong for exactly the arguments most likely to be passed. All 7 pass `format: "decimal"` on `.channels()`, not just `rgb` (whose unformatted default is a hex string) — bare is right at runtime for the other 6, but unprovable through faker's declarations, whose _first_ overload takes `format?: StringColorFormat` and returns `string`. `'decimal'` is `NumberColorFormat`'s sole member, so naming it is exact rather than a guess. The `T.array`-over-`T.tuple` choice is about _these_ methods' option-dependent arity, not a blanket rule — `location.nearbyGPSCoordinate`, whose `[latitude, longitude]` arity no option can change, is a `T.tuple([T.number, T.number])` and is checked by `Honest<...>` like any other method.
3. **Narrow the kind where faker's declared return type is narrower than its JS type.** A literal union becomes `T.enum.uniform([...])`, not `T.string`. A fixed-arity array becomes `T.tuple([...])`, not `T.array`.

Net surface: **26 modules, 237 ordinary builders, plus 14 from the 7 splits and 6 `use` forms — 257.** `test/Deviation.test.ts` asserts that as a **floor**, not an exact count — coverage is pinned at compile time (below), so a total would only duplicate it more weakly. The floor still earns its place: the type-level guards see `FakerModules/Types.ts` alone, so a builder lost in the mirror's _assembly_ (`Construct.ts`'s spread) is invisible to them.

### Hand-written, and why `tsc` is the enforcer

`test/index.types.test.ts`'s `Honest<$M, $K>` is what makes hand-writing safe: it compares each builder's `ValueOf<ReturnType<FakerModules[$M][$K]>>` against `ReturnType<Faker[$M][$K]>`. A method mapped to the wrong kind, an object entry with the wrong field shape, an enum missing a member, or a faker release changing a return type each fail `check` at the exact entry. It reads the _shipped_ surface, so what is asserted is precisely what consumers get. It is also what _finds_ rule 3's narrowings — the deviation worklist comes from `tsc`, not from a human enumerating it.

Faker drift has four independent surfaces, each with its own guard:

- **a module added/removed** — `_ModulesExhaustive`, comparing `keyof FakerModules` against `Exclude<keyof Faker, NotAModule>`. Checked against faker's own member list rather than a hand-kept roster, which could only ever confirm the mirror matches itself. Every exclusion is named: `helpers` per rule 1, plus the definition bags and instance members (`getMetadata`, `salt`, …) that share the key space without generating data.
- **a method added/removed on an existing module** — `MethodsExhaustive<$M>`, per module, `Equal<keyof FakerModules[$M], keyof Faker[$M]>`. Both faker module base classes declare their `faker` back-reference `protected`, so `keyof Faker[$M]` is exactly the public method set and needs no exclusions. `color` is equal too: a split node occupies the same key faker declares, with an object rather than a function behind it. `Equal`, not one-directional, so an upstream _removal_ fails as loudly as an addition.
- **a return type changed** — `Honest<...>`, above. Only `color`'s 7 splits are carved out of it, and only because each is one faker method but two builders, so the node isn't callable and there is no single return type to compare; they remain covered by `MethodsExhaustive`. Nothing else is exempt.
- **an overload set reordered** — no separate assertion. `FakerModules/Types.ts` spreads `Parameters<Faker[$M][$K]>` directly, so a reordering changes the declared parameters and the matching builder's `...args` forwarding stops compiling.

The peer is pinned at `^10.5.0` so faker 11 is an explicit opt-in.

**These guards resolve through `dist/`, so a src-only edit proves nothing until you rebuild** — the test files import via the package specifier (see "Tooling / conventions"). `bun run check` alone catches a `FakerModules/Types.ts`/`Build.ts` disagreement, since that is src-internal, but not a drift from faker.

### `FakerModules/Types.ts` is a literal type surface, and that is a performance requirement

`FakerExtension`'s module half is 237 **literal** property declarations, not a mapped type over a `Builders<$M>` helper. A mapped type must instantiate every member to resolve any one of them, so merely having the derived form in the program exhausted TypeScript 5's 5,000,000-instantiation budget and made every `toTypeBox(...)` call fail with `TS2589`. See "Tooling / conventions" for the `check:ts5` guard that makes any of this visible at all — `check` runs TypeScript 7, whose larger budget hides it.

The explicit builders and their 251 assignability checks measure ~54,700 TS5 instantiations against the 5,000,000 budget, a little over 1%. The budget hazard is specifically the mapped type, not volume of declarations.

**`FakerExtension` and `FakerModules` must be object-literal types, never `interface`s.** Only a literal type gets an implicit index signature, and `DeepMerge`'s `$AV extends PlainObject` test fails without one — silently degrading `registry.extend` from merging _into_ the faker node to replacing it wholesale. `test/Mergeable.test.ts` is the guard on that too.

`fakerExtension` carries an **explicit** `FakerExtension` return annotation. Its inferred type would reach into each kind's own `Schema` interface — internal to `@ghostry/fabricator` and unreachable from its `.` export — and declaration emission refuses to print an anonymous expansion of one. Same class of trap as the `TS4082` case above, and equally invisible to `tsc --noEmit`.

## JSR's "slow types" — a constraint neither `check` nor `build` enforces

`jsr publish` rejects any **public-API** symbol whose type it cannot read off the source syntactically. Four shapes trip it in this codebase, all of them in `Primitive/*/Registry.ts`, which reaches the public API through `registry`:

- a function without an explicit return type (`array`, `record`, and the builder methods on `bigint`/`string`);
- a `const` whose type is inferred — a trailing `satisfies` does not count, JSR wants an annotation (`Primitive/string/Constants.ts`'s `classes`, annotated member-by-member rather than with an index signature, because `Types.ts` derives `CharacterClass = keyof typeof classes` and an index signature would widen it to `string`);
- a **default export that is a call expression** (`null`, `undefined`), fixed with an `as` clause;
- a **default export whose object literal contains a spread** (`boolean`, `symbol`, `date`, `number`), fixed with an `as` clause. Where the annotation needs a name — a generic return type, or a literal carrying members beyond the spread — it is a local `ThisRegistry` alias, mirroring the `ThisMeta` spelling each `Schema.ts` already uses for the same "this module's own version of a shared concept" role, and never `Builder`, which `object/compute/Types.ts` already owns as a different concept. The member docs then live on `ThisRegistry`, since that is what a consumer's editor resolves to.

`tsc --noEmit` and `tsgo`'s declaration emit are both silent on this. **`bun run check:jsr` is the check** — per package, or the root fan-out across all three — and it is chained into every package's `test`, so CI's existing test step covers it with no workflow change. It runs `jsr publish --dry-run --allow-dirty`; `--allow-dirty` because JSR otherwise aborts on an uncommitted tree before reaching the type pass.

**The `DENO_BIN_PATH` in that script is the load-bearing part, not incidental.** The `jsr` npm CLI does not implement fast check itself and never consults `PATH`: it downloads the deno version pinned in `node_modules/jsr/dist/deno_version.js` into `node_modules/jsr/.download/<version>/<platform>/deno` and shells out to that. That pin lags the fast check JSR's own server runs, often by enough to matter — a bare `jsr publish` then succeeds while the server records the package as slow-typed, costing 5 of the 17 JSR score points with no error anywhere in the CI log. `DENO_BIN_PATH` overrides which binary it uses, and the root `deno` devDependency (the official distribution, `bin` + platform-gated `@deno/*` optional deps) is what makes that binary a pinned, lockfile-reproducible version rather than whatever a developer happens to have installed. **Pin it exactly — no `^`** — a floating range would let the strictness of the check drift between installs, which is the whole failure this guards against. Bumping it is a deliberate, reviewable change; expect it to surface new diagnostics, which is the point.

The authoritative post-publish signal is `allFastCheck` on `https://api.jsr.io/scopes/<scope>/packages/<package>/score` (rendered at `https://jsr.io/@<scope>/<package>/score` as "No slow types are used"). It is scored per version, so a fix only shows up once a new version publishes.

The `--allow-slow-types` escape hatch exists but is not used here: it degrades consumers' type-checking performance and JSR's generated docs.

When adding an annotation to satisfy this, verify it did not widen the public type rather than merely stating it. Copy each module's pre-change version into a scratch directory that sits at the same depth (`src/Primitive/__orig/`, so `../../` and `../<kind>` still resolve), then assert both directions in a throwaway file under `src/`:

```ts
type Exact<A, B> = [A] extends [B] ? ([B] extends [A] ? true : false) : false;
export const date: Exact<typeof oDate, typeof nDate> = true;
```

`bun x tsc --noEmit` failing with "Type 'true' is not assignable to type 'false'" is the annotation having changed the type.

## Documentation site (`docs/`)

`docs/` is a separate Vocs project — its own `package.json`/`bun.lock`, not part of the `pkg/*` Bun workspace, so the root's `bun install` never touches it. It sits outside every package's `tsconfig.json` `include`, so no package's `bun run check` ever sees it, and its own build runs under bun's runtime (`bunx --no-install --bun vocs build`, the `build` script) rather than the host `node` — `vocs`'s CLI imports `glob` from `node:fs/promises`, which needs Node 22+, so a bare `bunx vocs build` fails outright on an older host. Each package's own `jsr.json` `publish.exclude` keeps non-shipping directories out of its JSR tarball — `test` plus `src/playground.ts` for core and the adapter, `test` for the faker extension. `jsr publish` ships every non-gitignored file in the package directory by default, not just the module graph reachable from `exports`, so these exclusions are load-bearing, not decorative. `docs`/`.github`/`AGENTS.md` need no naming there at all: they live outside every `pkg/*` directory, not as excluded siblings the way they would if `jsr.json` sat at the repo root.

**`docs/package.json`'s one real dependency edge onto the workspace: `@ghostry/fabricator` as `file:../pkg/fabricator`.** This exists so twoslash-tagged code blocks (` ```ts twoslash `) can resolve and type-check real imports of the published package — without it, twoslash has nothing to check against. `bun` resolves `file:` specifiers by directory link, not build output, so `docs/`'s own `bun install` succeeds even against an unbuilt core — but `vocs dev`/`vocs build` then fail to resolve the module (and any twoslash block fails to check) until `pkg/fabricator`'s `dist/` actually exists. Building core is therefore a real prerequisite for working on `docs/`, not just for publishing it: `docs:dev` at the root builds core first for this reason, and `.github/workflows/docs.yml` installs and builds the whole root workspace before touching `docs/` for the same reason. Only core is wired in this way today; the adapter and faker extension packages would need the identical `file:` entry before any guide's code blocks could be twoslashed against them.

**Twoslash is on by default, with `explicitTrigger`.** Vocs's `rehypeShiki` defaults `twoslash: true`, so any fenced block tagged ` ```ts twoslash ` in `docs/src/pages/**` is compiled and type-checked at build time — a type error inside one fails `vocs build` outright (`throws: true` is also the default). It resolves `typescript` via `createRequire` against `docs/package.json` specifically (currently the `^5` devDependency there), and checks under twoslash's own near-default `compilerOptions` (`moduleResolution: bundler`, `types: ["node"]`, `preserveSymlinks: false` for the `file:` link above) — not `docs/tsconfig.json`, and not any `pkg/*` package's `tsconfig.json`. A snippet that type-checks under a package's own strict settings (`exactOptionalPropertyTypes`, `verbatimModuleSyntax`) is not thereby guaranteed to type-check under twoslash's, or vice versa.

**`renderStrategy: 'full-static'` in `docs/vocs.config.ts` is required, not optional.** Vocs's default (`'dynamic'`) is pure SSR: `bunx vocs build` under the default produces _zero_ HTML files, only `llms.txt`/`llms-full.txt`, with every page rendered at request time by `dist/server/serve-node.js`. GitHub Pages serves files and runs nothing, so the default is incompatible outright. With `'full-static'` set, the build additionally emits genuine prerendered HTML under `dist/public/` (`"IS_STATIC":true`, Waku's RSC flight data embedded inline, no server round-trip needed to hydrate) — verified by serving `dist/public` alone with a plain static file server, no Node process involved. **Only `dist/public` is the deployable artifact** — `dist/server` (and its `preview.js`/`serve-node.js`) exists for the Node-hosted deploy path this project doesn't use, and `.github/workflows/docs.yml` uploads `docs/dist/public` specifically, not `docs/dist`.

**Local `vocs preview` requires the `basePath` suffix in the URL, and the CLI's own startup message doesn't say so.** `docs/vocs.config.ts`'s `basePath` is set to `/fabricator` to match this site's GitHub Pages project-site URL (`docs.ghostry.dev/fabricator`). `bunx vocs preview` prints `Starting preview server at http://localhost:<port>` — no path suffix — but the preview server is `basePath`-aware and only serves under that prefix; requesting the bare root throws `error: pathname must start with basePath: /` (surfaces in-browser as a bare "Internal Server Error" with a server-entry stack trace, easy to mistake for a real bug). Always navigate to `http://localhost:<port>/fabricator/`. `vocs dev` behaves the same way. This is specific to _local_ preview — GitHub Pages' own routing performs the equivalent prefix mapping at the edge, so the deployed site needs no such workaround.

**A known Vocs defect under a non-root `basePath`: the "Skip to content" accessibility link never resolves correctly.** `vocs`'s `SkipToContent.client.js` builds its `href` from Waku's internal router path (`useRouter().path`), which doesn't carry the `basePath` prefix — so the link always points at `/#vocs-content` instead of `/fabricator/#vocs-content`, regardless of configuration. Low severity (keyboard-focus-only, one link, doesn't affect crawlers or normal navigation) and upstream, not something to patch around in this repo.

**`docs/src/pages.gen.ts` is gitignored, not committed** (`docs/.gitignore`) — it's a dev-server-only artifact, regenerated by a Vite plugin whose own definition is `apply: 'serve'` (`vocs`'s `fs-router-typegen.ts`), rewritten by a file watcher every time `vocs dev` runs and scans `src/pages/` for route changes. It's pure ambient `declare module 'waku/router'` type augmentation (typed route paths, e.g. for `<Link>`) — erased at compile time, never imported at runtime, and never touched by `vocs build`, which is what `docs.yml` actually runs. A from-scratch `vocs build` with the file absent succeeds and produces identical output. `docs/tsconfig.json`'s own `exclude: ["src/pages.gen.ts"]` (inherited from the `create-vocs` template) is the same signal — the file is generated output, not source, even though it lives under `src/`.

## Error handling — every throw is a named `FabricatorError` subclass

Every failure this library raises is a subclass of `FabricatorError` (`src/Error/index.ts`), never a bare `new Error(...)`. `FabricatorError` itself is abstract and holds no context — it exists only so `catch (e) { if (e instanceof FabricatorError) ... }` catches everything the library throws. Definitions live in that one file, kept dependency-free: kind tags are typed as plain `string` there rather than imported from `Primitive/index.ts`'s `Kind` union, both to avoid pulling the whole primitive graph into an unrelated import and because several of these errors exist precisely because the kind in hand was _not_ a member of that union.

Each subclass captures its failure's context as `public readonly` constructor parameters (a field name, an offending kind, a computed width) and assigns `this.name`/`this.message` in the body, following [`extern`'s `Error.ts`](https://github.com/pjrebsch/extern) shape. The message is still written to stand on its own — a consumer reading only `.message` shouldn't need a field to understand the failure — the fields exist for programmatic access and for context too bulky to inline (`UnknownOverrideFieldError`'s list of valid field names, say).

Classes are grouped by failure mode, not by call site: `InvalidOverrideValueError` alone covers every place `object/Registry.ts`'s `.override()` rejects a value against a field's kind (a plain field, a nested object, and each presence wrapper unwrapped to its inner kind), since all of those are the same failure with the same shape of context, just reached from different branches of one function.

Every subclass is declared inside `export namespace FabricatorError { ... }`, merged with the class of the same name — so there is exactly one thing to import, `FabricatorError` itself, and every subclass hangs off it: `FabricatorError.InvalidOverrideValueError`, `FabricatorError.UnknownKindError`, and so on. A call site never imports a subclass by its own name; it imports `FabricatorError` and writes `throw new FabricatorError.XError(...)`. This is also what `src/index.ts` re-exports — `export { FabricatorError } from "./Error"` carries every subclass out with it, so a consumer gets the whole hierarchy from one import, and `catch (e) { if (e instanceof FabricatorError) ... }` still catches all of it.

## Tooling / conventions

- Bun only — `bun test`, `bun x tsc --noEmit` (aliased as `bun run check`), never `npm`/`npx`/`node`.
- **`check` runs TypeScript 7; `check:ts5` runs TypeScript 5, and both are required.** The declared `typescript` is 7.x — the native port — whose type-instantiation budget is far larger than 5.x's 5,000,000. Most consumers are on 5.x, so a `check` that passes proves nothing about them: a program can be perfectly valid under 7 and fail under 5 with `TS2589` ("Type instantiation is excessively deep and possibly infinite"). `check:ts5` closes that blind spot, running the same `tsconfig.json` under a `typescript-5` npm alias (a second TypeScript installed under a distinct name so it can coexist without hijacking `node_modules/.bin/tsc`). It is chained into every package's own `test` script, so CI's existing per-package `test` step covers it with no workflow change. Verified to catch the real case: reintroducing one `const s: TString = toTypeBox(...)` annotation in `pkg/fabricator-extension-faker-v10` fails `check:ts5` and passes `check`.
- **Never annotate a `toTypeBox(...)` result with its expected TypeBox type; assert with `Expect<Equal<...>>` instead.** `const s: TString = toTypeBox(x)` forces TypeScript to check _structural assignability_ between `ToTypeBox<...>` — a ~20-branch conditional chain over recursive Schema interfaces — and a recursive TypeBox interface. That single check is expensive enough to exhaust TypeScript 5's whole budget in a program that is already large, and `pkg/fabricator-extension-faker-v10`'s is (a 237-property literal surface plus its 237 builders, plus `@faker-js/faker`'s own ~8,500-line declarations). `Equal<A, B>`'s identity comparison (`(<T>() => T extends A ? 1 : 2) extends ...`) skips the structural walk entirely, and pins the type _more_ precisely besides — `TUnion<[TLiteral<"female">, ...]>` rather than a loose `TUnion<TLiteral[]>`. This is why `pkg/fabricator-adapter-typebox-v0` asserts 81 conversions without trouble. Consumers are unaffected and need know nothing: their program carries only the built `dist/*.d.ts`, not these test suites, and an annotated conversion measures clean there.
- **Every test file imports its subject under test by package name, never by a relative `../src/...` path** — `@ghostry/fabricator`, `@ghostry/fabricator/internal` (for the genuinely internal modules a test needs — see `internal.ts`'s own doc comment for what's curated there and why), and `@ghostry/fabricator-adapter-typebox-v0`. This resolves through `node_modules` → each package's own `package.json` `exports` map → its built `dist/`, so `bun test` always exercises the actual build, matching the sibling `finity` repo's convention. The direct consequence: neither package's `check` nor `test` can run without `dist/` already existing — there is no source-based fast path. Each package's own `check`/`test` script does **not** build itself (so a downstream CI step can test a specific, already-downloaded build artifact without it being silently overwritten); the root `package.json`'s `check`/`test` scripts are what build first, unconditionally, before either package's own script runs. Running `bun run check`/`bun run test` from inside a package directory without a preceding build fails with `Cannot find module` — build from the root, or run that package's own `build` first.
- `verbatimModuleSyntax: true` — type-only imports must say `import type` (or `type` on individual specifiers) explicitly; this is enforced, not just style.
- `exactOptionalPropertyTypes` is **on** project-wide. A field's `?:` optionality (e.g. `T.omittable`'s effect on `Fabricated<$Definition>`) is a plain mapped-type key split (`OmittableKeys`/required split) that works the same regardless of this flag — but the flag is what makes `{ a?: string }` actually _mean_ "present with a string, or absent," rejecting `{ a: undefined }` at the call site rather than silently accepting it. Any optional property that's genuinely meant to accept an explicit `undefined` value (as opposed to "caller didn't pass this") needs `?: T | undefined`, not just `?: T` — see `number`/`string`'s `hints` and `Random/index.ts`'s `toRandomSource` options for the pattern: a param that's populated via `config?.field` naturally produces `T | undefined`, so the type it's spread into has to say so explicitly or this flag rejects it.
- Comments: TypeDoc-style `/** */` only, explaining _why_ (a constraint, an invariant, a workaround), never restating _what_ the code already says via naming. This codebase leans hard on this — most files have more doc comment than code, and the comments frequently cross-reference other files by name (`see Constructor.ts's make`) rather than duplicating explanation. Match that density when touching these files.
- **This file describes present-state facts and invariants, never change history.** No "originally shipped as," "used to be," "already bitten once," "was fixed the same way," "now" contrasted against a prior state, or narration of a bug's discovery/fix. State the current behavior and the trap directly (what's true, why it's true, what breaks if you get it wrong) — git history and commit messages are where "what changed" belongs, not here. When editing this file, rewrite any historical framing you encounter into a present-tense statement rather than preserving it.
- Test file organization is by _concern_, not by primitive: `As.test.ts`, `Compute.test.ts`, `Override.test.ts`, `Omittable.test.ts`, `Optional.test.ts`, `Undefinable.test.ts`, `random.test.ts` for runtime behavior; `*.types.test.ts` files (`Fabrication.types.test.ts`, `pkg/fabricator-adapter-typebox-v0/test/index.types.test.ts`, `pkg/fabricator-adapter-typebox-v0/test/Adapt.types.test.ts`) for compile-time-only assertions, using the `Equal`/`Extends`/`Expect` trick (a conditional-type equality check plus a `type X = Expect<...>` that fails to compile if false) rather than a runtime assertion library. A kind's `toTypeBox`/adapter-specific assertions live in the adapter package's own test suite even when the same concern's core-only assertions stay in `pkg/fabricator/test/` under the identical basename (`Always.test.ts`, `As.test.ts`, `Opaque.test.ts`, `Record.test.ts`, `Fabrication.types.test.ts` all split this way) — the two are independent files, not a shared one.
- Testing a probabilistic-roll kind (`boolean`, `object.omittable`, `object.optional` [3-way], `undefinable`) "sees every outcome across N draws" is deterministic per salt, not flaky in the usual sense — but a specific salt can still, legitimately, produce a short run that lands on one side for the first N draws. It'll pass reliably forever once fixed, since the same salt always replays the same sequence — but if a new test in this style fails, first try a wider sample (more elements / a higher retry cap) before suspecting the implementation; don't just pick a different salt string to make a failure disappear without understanding why, since that can just as easily paper over a real bug. `Optional.test.ts` also asserts the 33/33/33 distribution numerically (not just "all three outcomes occur"), specifically to guard against a regression back to the 50/25/25 a naive `omittable(undefinable(inner))` composition would give.
- Tests that compare multiple `initialize()` instances (same-salt replay, isolation, structural-keying siblings, …) must pass the **same `clock`** to each — `clock: "derived"` when they share a salt, a pinned `Date` when they don't (`"derived"` derives from the salt, so two different salts would still disagree on "now"). The unconfigured default is the wall-clock instant of that call, so two `initialize({ salt })` calls a millisecond apart silently diverge. Tests that specifically compare differently-clocked instances are the exception.
